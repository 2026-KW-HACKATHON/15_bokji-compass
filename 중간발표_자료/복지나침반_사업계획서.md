# 복지나침반 사업계획서 및 중간 개발 보고

> 공공 복지 정보를 정리하고, 사용자에게 필요한 공고와 확인할 이유를 안내하는 개인 복지 비서
>
> 작성 기준: 2026년 9월 23일 저장소 문서·코드 확인. 개발 검증 수치는 9월 21~23일의 기존 작업 기록을 인용했다. 이 문서를 작성하면서 외부 API·AI 모델·DB 통합 시험을 다시 수행한 것은 아니다.

## 1. 사업 개요

| 구분 | 내용 |
|---|---|
| 서비스명 | 복지나침반 |
| 해결하려는 문제 | 여러 기관의 공고 탐색, 복잡한 지원조건 이해, 사용자 상황에 맞는 정보 선별의 부담 |
| 핵심 사용자 | 복지·지원사업 정보를 찾는 일반 이용자, 복잡한 화면 사용에 어려움이 있는 시니어 |
| 제공 가치 | 개인 정보에 따른 공고 탐색과 추천 이유, 원문 확인 경로, 큰 글자와 단계별 입력 |
| 초기 제품 | React 기반 웹 시제품, 공공데이터 수집·조건 추출 백엔드 |
| 현재 단계 | 데이터 처리 기반과 웹 시연 화면 구현. 실제 추천 서비스를 완성하기 위한 저장·API 연결 단계 이전 |
| 향후 확장 | 검토된 정책의 저장·조회, 추천 API, 운영 배포. Android·iOS는 후속 확장 |

**중간 성과:** 공공 원문을 수집하고 AI로 조건 후보를 추출한 뒤 검증하여 파일 초안으로 저장하는 흐름과, 개인비서 형태의 웹 이용 흐름을 각각 마련했다.

**다음 핵심 목표:** 검토된 정책을 MySQL에 저장하고 공개 API로 웹에 연결하여, 실제 공고를 사용하는 시연을 완성한다.

## 2. 문제 정의와 대상 사용자

### 2.1 해결하려는 문제

1. **탐색 부담:** 기관별로 나뉜 정보를 사용자가 찾아다니고 자신과 관련 있는지 확인해야 한다.
2. **조건 해석 부담:** 나이·소득·가구·부모·예외 조건이 한 문서에 섞여 있으며, 같은 숫자도 적용 주체와 단위에 따라 의미가 달라진다.
3. **사용 부담:** 필터와 입력 항목이 많아지면 처음 사용하는 이용자가 다음 행동을 결정하기 어렵다.

탐색·사용 부담은 프로젝트의 문제 가설이며, 아직 사용자 인터뷰나 시장조사로 규모를 측정하지 않았다. 조건 해석의 어려움은 실제 정책 표본 분석에서 확인했다. [근거 S2, S5]

### 2.2 초기 사용자와 이용 장면

| 사용자 | 대표 이용 장면 | 제품 대응 |
|---|---|---|
| 청년·구직자 등 일반 이용자 | 지역·생활 상황·관심 분야에 맞는 공고 탐색 | 내 정보 입력, 추천 이유, 태그·분야·지역 검색 |
| 시니어·디지털 이용에 익숙하지 않은 사람 | 한 번에 적은 정보를 보고 순서대로 탐색 | 쉬운 화면, 큰 글자, 3단계 입력, 공고 한 개씩 보기 |
| 복지기관 상담 담당자 | 여러 정책과 이용자 상황을 함께 검토 | 향후 기관용 조회·상담 보조 도구 가능성 검토 |

기관용 서비스는 사업화 가설이며, 현재 계약·도입 기관·유료 고객이 확보된 상태는 아니다.

## 3. 서비스 구성과 사용자 경험

### 3.1 기본 이용 흐름

1. 지역·연령대·생활 상황·관심 분야를 입력한다.
2. 개인비서 화면에서 관련 공고와 추천 이유를 확인한다.
3. 검색·태그·필터로 공고를 더 탐색한다.
4. 관심 공고를 저장하고 상세 내용을 확인한다.
5. 공식 출처에서 최신 신청조건과 절차를 확인한다.

현재 개발 화면은 **합성 예시 공고와 결정적 추천 예시**로 이 흐름을 보여준다. 실제 공고 기반 서버 추천은 아직 연결되지 않았다. 추천 이유는 최종 수급 자격을 보장하지 않는다. [S4, S6]

### 3.2 쉬운 화면

- 기본 글자 20px, 주요 버튼·입력 높이 56px 이상을 기준으로 구현했다.
- 지역·연령, 생활 상황, 관심 분야의 3단계로 입력을 나눴다.
- 추천·검색·저장 공고를 한 개씩 보여주며 복잡한 조건을 접어서 표시한다.
- 단계 이동 초점과 키보드 탐색을 고려하고 모션을 줄였다.

브라우저 배치와 키보드 흐름 검증 이력은 있으나, 실제 시니어 참여 사용성 평가와 보조기기 검증은 남아 있다. [S5]

### 3.3 정보와 인증 처리

프로필은 기본적으로 메모리에 두고 사용자가 기억하기에 동의하면 브라우저에 저장한다. 현재 입력에서 주민등록번호·정밀 소득·정확한 주소는 수집하지 않는다. 로그인·회원가입은 입력폼만 구현했으며 계정 생성·인증 요청은 없다. [S4, S6]

## 4. 차별화 방향과 사업화 가설

### 4.1 제품 차별화 방향

| 설계 방향 | 구현 또는 목표 | 검증할 효과 |
|---|---|---|
| 추천 이유를 함께 제공 | 웹 표시 흐름 구현, 실제 서버 추천은 예정 | 사용자가 공고의 관련성을 이해하는지 |
| 원문 근거를 남기는 조건 구조화 | 인용·자료형·참조 검증과 초안 저장 구현 | 검토자가 잘못된 해석을 추적하기 쉬운지 |
| 정보 없음과 제한 없음 구분 | 파싱 계약에 상태와 실제 값을 분리 | 불확실한 정보를 자격 충족으로 오해하지 않는지 |
| 쉬운 화면 | 단계 입력과 한 개씩 보기를 구현 | 입력·탐색 완료율과 사용 시간 개선 여부 |

경쟁 서비스보다 우수하다는 비교 평가를 수행한 것은 아니다. 위 항목은 복지나침반이 검증하려는 제품 방향이다.

### 4.2 초기 도입 및 수익화 제안

**단기 제안:** 무료 웹 시제품으로 실제 공고 탐색 과제를 수행하게 하고, 추천 이유 이해도와 사용 완료 여부를 확인한다. 초기 참여자는 학교·지역 커뮤니티·복지기관 협조로 모집하는 방안을 검토한다.

**중기 가설:** 검증된 데이터 정리와 조회 기능을 기관의 상담 업무에 제공하고, 기관용 도구 운영·유지보수 또는 데이터 연동의 대가를 받는 모델을 검토한다. 도입 주체, 구매 의사, 공공데이터 활용 조건, 서비스 수준을 확인한 뒤 결정한다.

현재 시장 규모, 유료 전환율, 매출, 고객 확보 비용은 조사되지 않았다. 예산·매출 전망을 확정 수치로 제시하지 않는다.

### 4.3 비용 관리 항목

| 항목 | 산정 방식 제안 | 현재 상태 |
|---|---|---|
| 정책 분석 비용 | 처리 정책 수 × 정책당 평균 모델 사용량 × 적용 단가 | 표본 사용량 기록 있음, 비용 산정 미완료 |
| 서버·DB 운영 | 개발·시연·운영 환경별 호스팅과 저장·백업 비용 | Windows 개발환경 구성, 운영환경 미확정 |
| 데이터 품질 검토 | 초안 수 × 평균 검토 시간 × 검토 인력 단가 | 검토 절차와 소요시간 측정 필요 |
| 서비스 운영 | 모니터링·장애 대응·문의 처리 시간 | 운영 체계 수립 예정 |

수집 단계에서 조건을 정리하고 조회 단계에서 재사용하는 구조를 목표로 한다. 추천 설명에 별도 모델을 사용할지는 API 계약 확정 시 호출 비용과 함께 결정한다.

## 5. 시스템 설계와 구현 범위

### 5.1 기술 구성

| 계층 | 구성 | 역할 |
|---|---|---|
| 웹 | React·Vite | 개인비서 화면, 프로필, 공고 검색·저장, 쉬운 화면 |
| 서버 | Python·FastAPI | 환경설정, 서버 진입점, 상태·DB 연결 점검 |
| 수집·변환 | Gov24·복지로·공고 수집 모듈 | 원문 수집, JSON/XML·RawDocument 공통 입력 변환 |
| AI·검증 | Codex CLI, 공통 검증 코드 | 조건 후보 추출, 구조·원문 근거 검증, 실패 처리 |
| 현재 저장 | 로컬 JSON 파일 | 원문, 검토용 초안, 처리 이력 보존 |
| 후속 저장 | MySQL | 정책·조건·근거·개정 이력 저장 및 조회 예정 |

### 5.2 현재 동작하는 두 흐름

```text
데이터 처리: 공개 원문 파일 → 입력 변환 → AI 조건 추출 → 구조·근거 검증 → JSON 초안
웹 시연:    합성 예시 데이터 → 정보 입력 → 추천 이유 확인 → 공고 탐색·저장
```

두 흐름은 아직 실제 정책 저장소와 업무 API로 연결되지 않았다. MySQL 설정과 `/health/ready` 연결 확인이 존재해도 정책 적재 기능까지 구현된 것은 아니다. [S1]

### 5.3 후속 연결 구조

```text
초안 검토·승인 → MySQL 정책 저장 → 공개 공고 API → 웹·향후 모바일
사용자 프로필 → 후보 검색·추천 처리 → 추천 공고와 이유
```

서버는 검토 전 초안을 그대로 공개하지 않는다. 조건의 주체·숫자·단위·예외를 검토하고 실행 가능한 조건 논리를 확정해야 자격 판정에 사용할 수 있다.

**설계 결정이 필요한 부분:** 백엔드 계획은 검색·자격 판정을 코드로 수행하는 방향이며, 프론트 API 제안은 LLM 추천과 이유를 포함한다. 자격 판정과 추천 설명을 별도 책임으로 정의하고, 모델 호출 위치·비용·실패 동작을 공동 확정해야 한다. 현재 연령대 중심 프로필만으로 정밀한 수급 자격을 확정할 수는 없다. [S6, S7]

### 6.2 실증 결과

| 시점 | 실증 범위 | 확인한 결과 | 해석 범위 |
|---|---|---|---|
| 9월 21일 | 실제 공개 정책 6건 | 조건 후보 60개, 사전 선정한 구분 항목 8개 일치 | 6건 모두 부분 분석. 전체 정확도 수치가 아님 |
| 9월 22일 | 개선 파서로 정책 2건 | 조건 30개와 22개, 합계 52개 추출·구조/근거 검증 | 두 정책 표본의 결과이며 의미·단위 검토 필요 |
| 9월 22일 | 백엔드 오프라인 검증 | 테스트 71개, Ruff·의존성 검사 통과 기록 | 실제 운영 DB·전체 정책 검증을 의미하지 않음 |
| 9월 23일 | 프론트 검증 | 단위 테스트 12개, 포맷·운영 빌드 통과 기록 | 실제 추천 API 성공·전체 E2E 통과와 구분 |

6건 실험과 2건 파서 검증은 별도 실험이며, 서로 독립된 8건의 정책으로 합산하지 않는다. 구조·인용 검사 통과와 의미 해석의 정확성을 구분한다. [S2, S3, S4, S8]

### 6.3 기술적으로 얻은 결론

- 공통 코드는 ID·기본 필드·자료형·인용 검사를 담당하고, AI는 복합 조건의 주체·예외·문맥 해석 후보를 생성하도록 역할을 나눌 수 있다.
- 부모 소득과 신청자 소득, 가구 자산과 계약 보증금처럼 같은 키워드 안에서도 적용 대상이 다르다.
- 원문에 인용이 존재하더라도 잘못된 단위나 논리로 추출될 수 있다.
- 따라서 현재 모든 파싱 결과는 `draft`, `matching_enabled=false`를 유지한다.

### 예상 질문과 답변

**실제 AI 추천이 동작하나요?**

공개 정책 원문을 AI로 분석하는 백엔드 파서는 실제 호출 실증을 마쳤다. 웹의 개인별 추천은 예시이며, 실제 추천 서버 연결은 후속 단계다.

**DB는 완성됐나요?**

MySQL 접속 설정과 연결 점검은 구현했다. 정책 초안을 DB에 적재하고 조회하는 저장소는 아직 구현하지 않았다.

**정확도는 어느 정도인가요?**

6건 실험에서 조건 후보 60개를 얻고 선정한 8개 구분 항목을 확인했다. 이것을 전체 정확도로 볼 수 없다. 별도 검토 표본에서 누락·주체·단위·논리를 평가할 예정이다.

**왜 AI와 코드를 함께 쓰나요?**

코드는 공통 형식과 근거를 검증하기에 적합하고, AI는 문장에 섞인 적용 주체와 예외를 해석하는 후보를 만드는 데 사용한다. 결과는 검토 후 활용한다.

**수익 모델이 확정됐나요?**

초기는 무료 시제품 검증을 제안한다. 기관용 상담·조회 도구와 운영·연동 수익을 가설로 두고 수요와 비용을 조사해야 한다.

## 11. 참고 제안: 복지멤버십과의 차이 및 생활권 기반 확장

> **팀 미합의 참고안.** 이 절과 PPT 11~14장은 논의용이다. 기존 개발 성과, 확정 사업 범위, 4주 개발 일정에 자동 포함하지 않는다. 아래의 실제 제도 사례와 앞으로 구현할 서비스 아이디어를 구분한다. 2026년 9월 23일 차별화 검토 결과를 반영했다.

### 11.1 핵심 방향

**주민등록 주소지와 실제 사는 곳, 학교·직장이 있는 지역 및 사용자가 설명한 현재 상황을 함께 살펴서 놓치기 쉬운 지원을 찾고 신청 준비까지 돕는다.**

예를 들어 서울에서 생활하지만 청주에 주소를 둔 대학생에게는 청주와 연관된 주거·장학 공고를 계속 확인할 수 있게 하고, 서울 주소가 없어도 재학 등의 조건으로 지원 가능한 서울 사업을 함께 보여주는 방향이다. ‘모든 혜택을 빠짐없이 보장’하기보다는 수집 범위와 누락 가능성을 밝히고 관련 후보를 넓히는 것이 초기 목표다.

### 11.2 맞춤형 급여 안내와 공정하게 비교하기

정부의 **맞춤형 급여 안내(복지멤버십)**는 연령·가구·경제 상황과 공적자료를 바탕으로 받을 가능성이 있는 복지서비스를 안내하고, 생활 변화에 따라 다시 조사하는 제도다. [복지로 제도 안내](https://www.bokjiro.go.kr/ssis-tbu/twatza/wmAplyMng/selectWmGdnc.do)

2026년 1월 7일 정부 공식 소개에서는 **지자체 사업을 포함한 총 163종**으로 설명한다. 이 숫자는 해당 자료 시점의 안내 범위이며, 전체 복지정책 수나 중앙부처 사업 수가 아니다. [정부 공식 소개](https://www.korea.kr/news/policyNewsView.do?newsId=148957307)

복지멤버십의 안내 기능과 복지로 전체의 검색·온라인 신청 기능은 구분한다. 정부 전체와 비교할 때는 개인 상황 변화에 따른 맞춤 안내를 제공하는 **정부24 혜택알리미**도 비교 대상에 포함한다. [행정안전부 혜택알리미 소개](https://www.mois.go.kr/frt/bbs/type002/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000205&nttId=115124)

첨부 비교표에서 제시된 “변화 반영이 느리다”, “이해하기 어려운 단방향 안내”는 실제 속도·사용성 비교 전에는 가설로 취급한다. 복지나침반의 단계별 질문·쉬운 설명이 과제 수행에 도움이 되는지 평가하고, 관찰 결과로 차별화를 설명한다.

외국인 유학생 연결점은 광운대의 실제 프로그램 공고로 확인했으며, 월계1동 외국인 거주 인원이나 비율을 추정하지 않았다. 외국인을 하나의 자격집단으로 취급하지 않고 개별 사업의 국적·체류·재학 조건을 확인해야 한다. 다국어 안내는 후속 아이디어이며 현재 미구현이다. [광운대 KW&I 튜터링 안내](https://oia.kw.ac.kr/campus/notice.php?BoardMode=view&CURRENT_PAGE=1&UID=655)

### 11.4 민간 장학·동네 생활·일자리 확장

### 11.5 핵심 이용 사례: 청주 주소를 두고 서울에서 생활하는 학생

**가상 사용자:** 주민등록지는 청주, 실제 생활 장소는 서울 월계1동, 수도권 대학 재학. “이번 달 아르바이트가 끝나 생활비가 부족하다”고 설명한다. 부모 주소·주소 유지기간·학적 등은 추가 확인한다.

| 후보 | 공식 자료에서 확인한 사실 | 서비스가 설명할 내용 |
|---|---|---|
| 청주학사 | 청주시는 수도권 대학 재학생을 위한 공공기숙사를 운영. 지역 고교 졸업 또는 본인·보호자의 일정 기간 청주 주소 조건을 안내 | 서울 생활 중에도 청주와의 관계 때문에 확인할 후보라는 점과 학적·주소 기간·모집 시기 등의 추가 조건 |
| 청주·충북 관련 장학 | 지역 장학사업별 자격은 서로 다름. 확인한 대신정기화물 지정장학은 청주시 소재 대학 등 별도 요건을 제시 | “청주 주소이면 모든 지역 장학금 가능”으로 판단하지 않고, 재학 대학과 지역 요건의 조합을 확인 |
| 서울시 일경험 | 2026 서울영커리언스 가을학기 공고는 서울 소재 참여대학 재학생의 경우 거주지 무관 기준을 명시 | 서울 주소가 없어도 후보가 될 수 있으나 참여대학·연령·학적·근무 조건을 확인 |
| 기업 기부 장학 | 푸른등대 삼성기부장학금 등 기업 기부 기반 사업 존재 | 주소 외에 전공·학적 등 해당 사업 기준과 신청기간 확인 |

근거: [청주시 청년 주거정책·청주학사](https://www.cheongju.go.kr/www/contents.do?key=22708), [충북인재평생교육진흥원 지정장학 공고](https://www.cbitle.or.kr/www/selectOnlineRceptWebView.do?key=57&onlineRceptNo=6&pageIndex=1&pageUnit=10&searchCnd=all&searchOnlineRceptSttus=&searchRceptBgndt=&searchRceptEnddt=&searchRceptNm=), [서울시 공고 제2026-1816호 원문 사본, 대학 게시](https://kau.ac.kr/upfile/2026/06/15/20260615104012-1652.pdf), [삼성기부장학 안내](https://www.kosaf.go.kr/ko/scholarnf.do?pg=scholarship05_25_04).

청주학사와 충북·기업 지정장학은 서로 다른 운영 사업이다. **서울 재학생에게 적용되는 청주시 자체 장학금의 구체 사업명·전체 조건은 이번 확인에서 확정하지 않았으므로 탐색 대상으로 남긴다.** 위 인턴십도 모든 서울 대학이 대상은 아니며, 광운대 참여를 확인한 것으로 표현하지 않는다. 사례는 지역 조건 설계를 위한 자료이고 현재 신청 가능 목록이 아니다.

**제안 화면 문구:** “청주와 연관된 주거 지원 후보를 찾았습니다. 서울 생활 여부와 별도로 청주 고교 졸업 또는 본인·보호자 주소 유지기간을 확인해 주세요.” 이후 추천 근거, 미확인 조건, 모집 상태, 원문 링크를 함께 제시한다.

대화에서 파악한 소득 감소는 생활비·장학·일자리 후보를 찾는 단서다. 이번 달 소득이 없다는 사실을 모든 사업의 소득 기준 충족으로 변환하지 않는다. 각 공고의 산정 기간·가구 범위·증빙 기준을 별도로 확인한다. 자연어 입력과 추가 질문은 현재 웹 폼에 구현된 기능이 아니다.

### 11.6 구현하려면 추가할 정보와 팀 논의

현재 프로필의 단일 `region`으로는 위 사례를 충분히 표현할 수 없다. 다음 항목은 **설계 제안이며 코드에 반영하지 않았다.**

| 항목 | 필요한 구분 |
|---|---|
| 지역 | 주민등록지, 실거주지, 재학 지역, 근무 지역, 필요한 경우 보호자 주소지 |
| 관계와 기간 | 누구의 주소인지, 언제부터인지, 공고 기준일, 관내 고교 졸업 여부 |
| 신청자 상태 | 학생·휴학생·구직자, 필요한 사업에 한해 전공·학년·국적·체류 요건 |
| 공고 조건 | 주소 또는 재학 중 하나인지, 둘 다 필요한지, 모집 기간과 변경 이력 |
| 설명 | 추천 근거, 확인할 조건, 신청 마감, 접수처, 원문 출처 |

주소는 필요한 행정구역 수준부터 선택 입력하고, 특정 공고 확인에 필요한 정보만 추가로 묻는 방식을 제안한다. ‘거주’라는 원문을 모두 주민등록으로 바꾸지 않고 원문 정의를 유지한다. 정보 부족은 부적격으로 확정하지 않는다.

팀에서 먼저 합의할 사항은 ① 월계1동을 초기 검증 지역으로 삼을지 ② 민간 장학·생활 프로그램·일자리 중 우선 수집 범위 ③ 지역·학적 정보 입력 범위 ④ 정보 연결과 직접 알선의 경계 ⑤ 최신 모집 상태를 검토할 담당과 주기다.

**차별화 검증 제안:** 동일한 가상 프로필로 기존 공식 서비스와 복지나침반 후보 목록을 비교해 추가로 발견한 유효 공고, 잘못 추천한 공고, 신청 경로 확인 시간과 이유 이해도를 측정한다. 이 결과를 얻기 전까지 독자적 우위나 정보 포괄성을 확정하지 않는다.

### 11.7 해커톤 차별화 후보의 우선순위

| 제안 | 판단 | 시연 범위 제안 | 현재 상태 |
|---|---|---|---|
| 민간·지자체 정보 확장 | 우선 검토 | 월계1동 생활권, 대학·기업 장학, 지역 일자리의 유효 공고와 추천 근거 | 일부 공공·대학 수집 기반만 구현. 민간 포괄 수집 미구현 |
| 현재 상황의 대화형 탐색 | 핵심 후보 | 사용자 문장에서 지역·생활 상황 추출, 부족한 조건 추가 질문, 근거 있는 후보 제시 | 자연어 추천·질문 흐름 미구현 |
| 신청 프로세스 자동화 | 준비 보조부터 | 필요한 서류와 접수처 안내, 작성 가능한 신청서 초안 제공, 사용자 확인 | 미구현. 실제 대행 제출 API 확보·기관 연계 없음 |
| 커뮤니티·후기 | 후속 검토 | 공고 연도·유형별 준비 과정과 접수 팁 공유 | 미구현. 운영·검토 정책 필요 |

데이터 수집 방식은 **공식 API와 기관별 공고 수집**으로 표현한다. SaaS는 서비스 제공 방식이므로 크롤링과 같은 수집 기술로 나열하지 않는다. 해커톤 초기 범위는 장학·주거·일자리·생활지원에 집중하는 안을 제안한다. 배달앱 등 일반 할인정보는 최신성 관리와 제품 범위가 커지므로 후순위로 둔다.

AI 작성 범위는 사용자가 제공한 정보에 기반한 신청서 초안으로 제한하고, 기관 발급 증명서를 생성한 것으로 표현하지 않는다. 실제 대행 신청은 해당 기관의 API·본인인증·동의·연계 권한을 확인한 후 별도 범위로 결정한다. 현재 제안된 조회·추천 API를 신청 API로 설명하지 않는다.

후기는 신청 준비 참고자료이며, 다른 사람의 선정 경험을 사용자의 자격 충족 근거로 사용하지 않는다. 개인정보 노출과 오래된 모집조건을 관리할 운영 방법을 정해야 한다.

**발표용 제안 문장:** “복지나침반은 주소지·실거주지·재학·근무 지역과 현재 상황을 함께 살펴, 지역·대학·민간의 지원 기회를 찾고 신청 준비까지 돕는 생활밀착형 안내 서비스를 지향합니다.”

기존 계획의 실제 데이터 저장·API 연결을 우선 진행하면서, 위 후보 중 시연 가능한 하나를 팀에서 선택한다. 제안을 문서에 추가한 것이 개발 완료나 팀 합의를 의미하지 않는다.
