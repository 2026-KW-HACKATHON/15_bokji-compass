# 복지나침반 중간 개발 보고서

팀명: 복지나침반 / 발표자: 송현오 / 조 번호: 제출 전 확인

발표일: 2026-09-28. 작성 기준: 2026-09-27 로컬 저장소 `8d2d320`의 코드와 문서. 운영진 지정 양식은 제공받지 않았으므로 아래는 양식 반영용 초안이다.

## 1. 문제와 목표

복지나침반은 공공 복지·지원사업 공고를 수집하고, 조건과 원문 근거를 정리해 사용자에게 관련 정보를 안내하는 개인 복지 비서다. 사용자는 공고를 찾은 뒤에도 연령·지역·가구·소득·재산·예외 조건의 의미를 해석해야 한다. 특히 부모와 신청자의 소득, 가구 자산과 계약 보증금처럼 적용 대상이 다른 값을 구분해야 한다.

문제 가설은 공고 탐색 및 조건 이해의 부담이다. 실제 공고 표본에서 복합 조건을 확인했으나 사용자 인터뷰로 불편의 빈도나 시장 규모를 측정하지는 않았다. 사용자가 지정한 실제 발표 PPT에 맞춰 월계1동을 첫 검증 범위로 두고, 지역 어르신의 화면·절차 부담, 타지역에서 온 청년의 주소지·생활지역 구분, 외국인 유학생의 용어·자격 조건 이해를 초기 이용 상황으로 설정한다. 집단별 수요와 인구 비중은 확인 전이며, 지역 확장·외국인 자격 판정이 완료됐다는 뜻은 아니다.

제품 목표는 사용자가 자신의 상황에 관련된 공고와 그 이유를 이해하고, 공식 원문에서 신청조건을 확인하도록 돕는 것이다. 최종 수급 자격이나 선정을 보장하지 않는다.

## 2. 사용자 시나리오

1. 지역·연령대·생활 상황·관심 분야를 입력한다.
2. 관련 공고와 추천 이유를 확인한다.
3. 필요한 공고를 검색·저장하고 상세 정보를 읽는다.
4. 공식 출처에서 최신 조건과 신청 절차를 확인한다.
5. 필요하면 소득·재산 참고 계산을 사용한다. 회원은 동의 후 금융 원입력을 저장하고 삭제할 수 있다.

쉬운 화면은 입력을 3단계로 나누고 공고를 한 개씩 표시한다. 큰 글자와 버튼, 키보드 흐름을 고려했다. 실제 사용자 평가 효과는 미측정이다. 웹의 공고·추천 흐름은 현재 합성 예시 데이터로 동작한다.

## 3. 시스템과 입출력

| 구성 | 입력 | 처리·출력 | 상태 |
|---|---|---|---|
| 공고 수집 | Gov24·복지로·기관 공고 | 원문과 출처 보존, 공급자별 입력 변환 | 수집 모듈 구현, 자동 전체 수집·스케줄러 후속 |
| 조건 추출 | 공개 JSON/XML 및 원문 | 명확한 조건은 코드 처리, 미해결 문맥은 AI 후보 추출 | 구현 및 기존 호출 실증 기록 |
| 검증·정규화 | 추출 후보와 원문 | 자료형·인용·참조 검사, 표준 조건과 공식 지역 코드 | 구현, 의미 검토와 공개 승인 후속 |
| 초안 저장 | 분석·정규화 결과 | `draft.json`, manifest, 시도별 진단 파일 | 로컬 파일 구현 |
| 웹 | 추천용 프로필·합성 공고 | 예시 추천 이유, 검색·저장·쉬운 화면 | 시연 구현 |
| 인증 | 가입·로그인 입력 | 계정·세션·로그아웃 | 구현, 문자 인증은 개발용 |
| 금융 계산 | 가구·소득·재산·부채·차량 원입력 | 서버 규칙에 따른 참고 계산과 추가 확인 항목 | 공개 계산·동의 기반 회원 저장 구현 |
| 실제 정책 서비스 | 검토·승인한 공고 | MySQL 정책 저장·조회, 공고·추천 API | 미구현 |

기술 구성은 React/Vite 웹, Python/FastAPI 서버, SQLAlchemy 기반 DB 연결과 MySQL 목표 저장소다. 인증·회원 금융 저장의 격리 SQLite 검증 이력과 정책 저장소 구현을 구분한다.

조건 스키마는 주체·필드·값·연산자·단위·기준일·근거를 분리한다. 상태 0은 명시적 제한 없음, 1은 값 있음, 9는 정보 없음이다. 값 0원과 미입력을 구분한다. 논리 조합은 `all/any/not/unknown`을 사용하고, 검토 전 파싱 결과는 `review_status=draft`, `matching_enabled=false`로 유지한다.

## 4. 차별화 가설

복지나침반은 조건의 주체·단위와 원문 근거를 추적하는 데이터 구조를 쉬운 탐색 화면과 결합하는 데 집중한다. 사용자가 단순히 공고 목록을 받는 데서 그치지 않고 왜 관련이 있고 무엇을 추가 확인해야 하는지 이해하게 하는 것이 목표다.

기존 서비스에 맞춤 안내 기능이 없다고 가정하지 않는다. 경쟁 우위와 사용자 편익은 아직 검증 전이다. 동일한 공고 탐색 과제로 원문 도달률, 조건 이해도, 소요시간을 비교할 계획이다. 여러 생활권·민간 공고 확장·신청 준비 보조는 기존 문서의 팀 미합의 제안이며 현재 확정 구현 성과에 포함하지 않는다.

## 5. 중간 성과와 검증 한계

2026-09-21 실험 기록은 공개 정책 6건에서 조건 후보 60개를 추출하고 사전 선정한 구분 항목 8개를 확인했다. 6건 모두 부분 분석이며 완전한 자격 판정은 0건이었다. 이 수치는 전체 정확도나 실제 추천 성능이 아니다. 별도 후속 2건 실험과 합산하지 않는다.

현재 코드는 정책 수집·파싱·조건 정규화와 웹 시연, 서버 인증, 소득·재산 참고 계산을 포함한다. 기존 9월 23일 보고서의 ‘인증 입력폼만 구현’ 설명은 최신 상태와 다르다. 실제 SMS 공급자, 정책 저장·추천 API, 사용자 대상 효용 검증은 남아 있다.

본 문서 작성 시 과거 외부 AI 호출과 실제 MySQL 저장을 재시험하지 않았다. 과거 테스트 개수를 현재 실행 결과로 제시하지 않는다. 상세 검증 범위와 실행 조건은 아래 재현 절을 기준으로 한다.

2026-09-27 이번 준비에서 웹 `npm test`의 단위 테스트 22개가 통과했다. 실제 브라우저에서 쉬운 화면의 3단계 입력 후 예시 추천 이유와 공고 한 개 표시를 확인했고, 해당 화면을 이번 PPT에 사용했다. 백엔드 전체 테스트와 실제 정책·추천 API 통합 시험을 통과했다는 의미는 아니다.

### 6.2 웹 예시 재현

저장소를 받은 뒤 `frontend/web`에서 다음을 실행한다. 서버는 개발 기본값인 예시 모드로 시작한다.

```powershell
npm ci
npm test
npm run dev -- --port 5173 --strictPort
```

5173 포트를 사용 중이면 사용하지 않는 포트로 바꾼다. 브라우저에서 터미널에 표시된 주소를 연다. ‘내 정보’에서 거주 지역을 서울, 관심 분야를 주거로 선택하고 추천받기를 실행한다. 기대 결과는 예시 표시와 추천 이유가 나타나는 것이다. 쉬운 화면을 켜면 공고를 한 개씩 표시한다. 원격 AI 호출 성공이나 실제 공고 적격 판정을 의미하지 않는다.

`npm test`는 웹의 입력·추천 요청·금융 모델 등에 대한 단위 검증이며 실제 백엔드나 DB의 통합 검증을 대신하지 않는다. 인증과 계산기의 정상 응답 시연에는 별도로 백엔드를 실행해야 한다.

### 6.3 백엔드 검증

프로젝트 루트에서 `backend/readme.md`에 따라 환경을 구성한 후 다음을 실행한다.

```powershell
.\backend\scripts\test.ps1
```

이 검증은 실제 운영 DB·LLM 호출 없는 테스트다. 외부 모델 파싱을 재현하려면 공개 가능한 원문 입력 파일과 해당 PC의 CLI 설치·로그인 및 설정이 필요하다. 키나 계정을 Git에 넣지 않는다. 실제 파싱 명령과 입력 형식은 `backend/docs/raw-parsing.md`를 따른다.

과거 6건 실험의 전체 입력·출력은 Git 제외 `backend/data/classification-experiments/`에 기록되어 있다. 새로 클론한 저장소만으로 과거 호출 산출물 전체를 재현할 수 있다고 주장하지 않는다. 기획 문서 재현성을 높이기 위한 다음 보완은 공개 가능한 표본 원문, 실행 설정, 모델 버전과 기대 검증 항목을 작은 재현 패키지로 제공하는 것이다.

### 6.4 최종 통합 시연 완료 기준

검토한 실제 공고 1건 이상을 저장하고, 서버 재시작 후에도 API로 조회하며, 웹에서 입력·추천 이유·원문 출처를 확인한다. 정상 결과 외에 정보 부족, 조건 미충족, 빈 결과, 서버 오류 경로도 확인한다. 이 문단은 앞으로 달성할 완료 기준이며 현재 통과한 결과가 아니다.

## 7. 다음 개발 계획

최종발표 날짜와 인력 배분이 제공되지 않아 날짜·개인 담당자는 확정하지 않았다. 기존 4주 제안 일정을 그대로 이번 해커톤 일정으로 주장하지 않고 아래 의존 순서로 우선순위를 정한다.

| 순서 | 책임 역할 | 산출물 | 완료 기준 |
|---|---|---|---|
| 1 | 데이터·백엔드 | 공개할 공고와 검토 기준 | 원문·주체·단위·예외 검토 완료 |
| 2 | 백엔드 | 정책 저장·조회 | 중복·개정·롤백·재시작 후 조회 검증 |
| 3 | 백엔드·프론트 | 실제 공고 API 연결 | 웹에서 공고·이유·원문 확인, 오류 처리 |
| 4 | 팀 공동 | 사용자 과제 평가 | 완료율·시간·도움 요청·조건 이해도 기록 |

네이티브 앱, 커뮤니티, 신청 대행 등의 추가 범위보다 실제 데이터 연결을 우선한다. 역할별 개인 담당자와 일정은 팀 회의에서 기입한다.

## 8. 실현·사업화 가능성

초기에는 무료 웹 시제품으로 탐색 과제를 검증한다. 기관 상담용 조회 도구, 운영·유지보수와 데이터 연동의 유료 수요는 가설이다. 현재 유료 고객, 계약, 매출, 시장 규모 수치는 없다.

기관 인터뷰에서는 현재 공고 확인에 드는 시간, 데이터 갱신·검수 책임, 도입 의사와 예산 범위를 확인한다. 운영비는 수집·변경 공고 수, 공고당 모델 사용량, 검토 시간, 서버·DB 비용으로 나눠 실측한다. 명확한 조건을 코드로 먼저 처리하고 검토한 데이터를 재사용하는 구조의 비용 효과도 측정한다.
