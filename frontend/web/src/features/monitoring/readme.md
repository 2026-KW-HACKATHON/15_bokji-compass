# 계정에 저장하는 지속 복지 안내

## 신청하기와 준비 서류 확인 (2026-10-08)

추천 카드의 `ApplicationGuide`에서 ‘이 공고 신청하기’를 펼치면 원문에 확인된 신청
주소·신청 전화·문의 전화·방문 안내와 조건부 서류를 보여준다. 주소·번호·필수 서류를
추정하지 않고 공식 안내 링크와 실제 신청 링크를 구분한다. 양식 없음은 구비서류
없음으로 바꾸지 않는다. 원문 메타데이터는 번역된 공고에서 추출하지 않는다.

계정의 현재 후보에서 준비 여부를 체크한다. `monitoringApi.preparation`은
`{policy_id, need_id, revision_id, document_id, prepared}`만 보내며 응답으로 체크를
확정한다. 실패는 이전 체크를 유지해 재시도하고 409에는 공고 재확인을 안내한다.
`monitoringModel`은 이전 응답을 null로 처리하며 공고 변경 시 과거 체크를 새 서류에
적용하지 않는다. 표시 개수는 준비한 서류이며 신청 완료·자격 충족을 뜻하지 않는다.
이전 기록은 읽기 전용이고 확인된 마감 공고에는 신청 액션을 제공하지 않는다.
다국어 UI·44px 조작 영역을 제공하고 조건부 서류 문장은 원문 그대로 유지한다.

## 추천 제외와 이유 선택 (2026-10-08)

현재 추천 카드에서는 진행 상태 선택 대신 하단의 작은 밑줄 버튼 ‘이 공고 추천하지 않기’를
표시합니다. `RecommendationFeedbackForm`의 라디오로 ‘지원 대상이 아니에요’ 또는
‘관심 없는 공고예요’를 선택해야 저장할 수 있습니다. 관심 없음은 비슷한 공고 순위를
낮춘다는 설명을 표시합니다. 취소는 저장하지 않고 버튼에 포커스를 돌려주며 실패 시
선택 이유를 유지해 다시 시도합니다. 저장 중 중복 제출은 막습니다.

`monitoringApi.feedback(candidate, reason, {signal})`은 공고·탐색 분야 ID와 선택 이유만
인증 API에 보냅니다. 저장된 snapshot에서 제외한 공고는 현재 후보와 추가 질문에서
빠지고 ‘추천에서 제외한 공고’ 목록에 이유와 ‘다시 추천받기’를 제공합니다. 복원은
`reason:null`입니다. 새로고침·다른 기기에서도 계정에 저장된 설정을 사용합니다.

`monitoringModel`은 새 필드를 검증하며 이전 응답의 미제공 필드는 빈 목록으로 처리합니다.
기존 신청 상태는 보존하고 AI 비서의 ‘신청 현황’과 이전 신청 기록에만 기존 선택을
표시합니다. 버튼은 44px 터치 영역·키보드 포커스·필드 그룹을 갖추고 5개 언어를 지원합니다.

2026-10-08 종 디자인 보완: 배지는 일반 화면 16px/9px 글자, 쉬운 화면 20px/11px
글자로 조정했습니다. 배지 경계는 헤더 배경과 같은 1px 선을 사용하고 종의 선은 1.5로
완화했습니다. 쉬운 화면의 사각 외곽선을 제거하고 40px/56px 조작 영역·키보드 초점은
유지합니다. 공개 함수·미읽음 수·읽음 API 계약은 바뀌지 않습니다.

2026-10-08 회원 알림: `NotificationBell`이 회원명 옆 종·미읽음 배지와 최근 알림 목록을
표시합니다. `useAlertNavigation`은 최신 공고 상세·404 시 관련 안내 이동과 읽음 처리를
공유합니다. 패널은 `onOpenAlert(alert)`·`openingAlertId`를 받아 알림 본문도 클릭할 수
있습니다. `monitoringEvents.js`는 수정 성공 뒤 데이터 없는 무효화 이벤트로 배지와
본문을 갱신하며 편집 초안은 보존합니다. [호출·오류·계정 경계](../../../../docs/notification-inbox.md).

2026-10-08 신청 확인사항: 후보 카드의 제목은 ‘신청 전 확인사항’이며 서버가 제공한
공고 원문의 신청 대상·제외 안내를 표시한다. `parseMonitoringSnapshot()`은
`userReviewQuestions(questions, need.questions)`로 이전에 저장된 내부 추출 키·막연한
반복 문구를 공식 공고 확인 안내 하나로 정리하고 생활정보 질문의 카드 중복을 제거한다.
원문 조건, 진행 상태, API 저장값은 보존하며 생활정보 질문은 별도 확인 영역에 유지한다.

`MonitoringPanel`은 독립 AI 복지비서 페이지(`#assistant`), AI 비서 하위의 지속 복지 안내(`#assistant-monitoring`), 내 정보 하위의 신규공고 확인하기(`#new-notices`)에서 같은 계정 정보를 조회합니다. 회원 정보(`#profile`) 본문에서는 지속 안내와 새 안내 목록을 제거했습니다. 기존 브라우저 추천 설정과 별도로, 생활정보 저장 동의와 지속 안내 활성화 여부를 관리합니다. 기본값은 꺼짐이며 모르는 사실은 `null`로 유지합니다. 기본 홈에는 AI 복지비서로 이동하는 진입 버튼을 둡니다.

`MonitoringPage({notices = false, ...panelProps})`는 페이지 제목·상위 메뉴·서로의 이동 링크와 패널을 반환합니다. `notices=false`는 `variant="guidance"`로 설정·지원 분야·후보·진행 상태를, `true`는 `variant="notices"`로 새 안내와 개별/일괄 읽음만 표시합니다. 알림 전용 페이지에서는 생활정보가 없어도 빈 상태·중지 상태를 표시하며 폼을 열지 않습니다. 요청/오류/재시도/취소/계정 분리는 기존 패널과 공개 monitoring API를 재사용합니다. 비회원 로그인은 방문한 하위 페이지로 복귀합니다.

## AI 복지비서의 정보 입력 흐름 (2026-10-08)

`variant="assistant"`에서는 저장한 정보가 없을 때 빈 통계·대형 요약 카드·상세 메뉴 대신
‘내 정보부터 간단히 알려주세요’ 카드와 ‘내 정보 입력하기’를 표시합니다. 입력 버튼은
이미 등록된 회원 나이·지역 요약보다 먼저 배치합니다. 나이와 지역은 회원 정보에서
가져오며 이 폼에서 다시 수집하지 않습니다. 수정 링크가 다른 화면으로 이동한다는 점과
작성 중인 내용은 먼저 저장해야 한다는 점을 알립니다.

`AssistantProfileForm`은 일·학업 상태, 가구, 구직 여부와 관심 분야를 한 페이지에서
입력합니다. 주거·최근 피해 정보는 필요할 때 펼치는 선택 항목이며 저장된 값이 있으면
처음부터 펼칩니다. 편집 중에는 다른 관리 내용을 감추며 취소하면 진입 버튼에 포커스를
돌립니다. 저장에 실패하면 초안을 유지하고 오류 안내로 포커스를 옮깁니다.

모든 정보는 선택 사항입니다. 미확인 `null`과 명시적인 ‘아니요’ `false`를 구분하며 나이,
직업, 관심 분야나 거주 지역만으로 구직·소유·피해 여부를 추론하지 않습니다. `/profile`은
전체 교체 계약이므로 기존 snapshot의 전체 프로필을 복사해 입력을 시작하고 접힌 항목과
미수정 값을 보존합니다. 저장 동의는 매번 직접 선택하고, 최초 지속 안내는 꺼져 있습니다.
‘새 공고도 계속 알려받기’는 별도 선택이며 수정 시 기존 활성 상태를 유지합니다. 안내가
꺼지면 ‘내 정보 저장하기’, 켜지면 ‘저장하고 지원 찾기’로 동작을 구분합니다. 안내를 끄고
저장했을 때에는 검색 완료를 주장하지 않고 ‘새 공고 안내 켜기’로 이어집니다.

저장 후에는 작은 내 정보 요약과 안내·신청 수를 표시합니다. 가구와 관심 분야도 요약에
포함하며 ‘맞춤 지원 / 신청 현황 / 새 안내 / 내 정보’ 네 메뉴와 별도 추가 확인 버튼으로
기존 상세 기능에 접근합니다. `variant="guidance"`는 새 안내 목록을 제외한 기존 관리 화면을 유지합니다.

## 파일과 연결

- `monitoringModel.js`: 선택값·실제 서울 날짜·서버 snapshot 검증. 명시적인 피해 없음/수리 불필요 값을 보존하며 날짜나 주거 상태를 추정하지 않습니다. 후보 공고 ID를 검증하고 기존 `parsePolicy`/공식 URL 검증을 사용합니다. `scan_status: unavailable`은 저장 실패로 취급하지 않습니다.
- `monitoringApi.js`: `/v1/monitoring` 조회와 `/profile`, `/preferences`, `/refresh`, `/candidates/state`, `/alerts/read`, `/delete` 수정. 모든 요청은 인증 세션을 사용합니다. 계정 ID는 클라이언트에서 보내지 않습니다.
- `MonitoringPanel.jsx`: 선택형 일·가구·주거·재난 정보, 관심 분야, 별도 저장 동의, 지원 분야·추천 이유·미확인 조건·지원 후보와 진행 상태, 새 안내 읽음, 중지·재개·삭제 UI.
- `AssistantProfileForm.jsx`, `assistant-profile-form.css`: 독립 비서 페이지의 한 페이지 선택 입력 폼, 회원 정보 요약, 별도 저장 동의·안내 선택, 오류·입력 포커스와 반응형 배치.
- `monitoring.css`: 기존 색상과 버튼을 사용하는 반응형 패널. 320px과 쉬운 화면에서는 후보·입력 항목을 한 열로 배치합니다.

`App`이 `user.id`로 패널을 mount합니다. 계정 전환/로그아웃/페이지 이동은 모든 요청을 취소하고, 늦은 응답은 mount와 계정 ID 확인 후 적용합니다. 저장이 실패하면 입력한 초안과 기존 후보를 유지합니다. 공고 확인이 실패하면 최근 성공 시각과 기존 후보를 유지하며 실제 실패 안내를 표시합니다.

활성화된 화면은 60초마다, 화면으로 돌아올 때 저장된 snapshot을 다시 읽습니다. 이는 공고를 평가하는 작업이 아니라 서버에 쌓인 안내를 표시하는 조회입니다. 공고 다시 확인은 서버 `/refresh`를 호출합니다. 서버의 주기 작업을 실제 운영 환경에서 별도로 실행해야 브라우저를 닫은 동안에도 공고 비교가 이어집니다.

재난 피해는 사용자가 직접 확인한 입력을 사용합니다. 외부 지역 재난 자동 감지와 외부 푸시·메일 전송은 연결되지 않았으므로 수신을 약속하지 않습니다. 지원 후보는 최종 신청 자격 확정이 아니며 공식 공고와 담당 기관에서 추가 조건을 확인해야 합니다. 지원 진행 상태는 사용자가 선택한 기록이며 실제 기관의 접수 결과가 아닙니다. 표시된 안내 읽음은 현재 snapshot에 포함된 안내만 처리합니다.

회원 거주 지역을 바탕으로 원문에 재난 지원 근거가 있는 등록 공고를 자동 탐색하는 `disaster_watch`도 동적으로 표시합니다. 피해 여부가 미확인인 경우 실제 피해 여부·발생일을 질문하며 모든 후보는 `needs_review`입니다. 피해 없음 저장 시 해당 탐색을 억제하고, 피해 있음 저장 시 발생일이 미확인이어도 `disaster_recovery` 분야를 이어서 표시하며 발생일을 추가 확인합니다. 이는 관련 지원 공고의 자동 발견이며 실제 재난 발생 감지가 아닙니다.

주택 소유 옵션은 본인 소유와 가족 소유 등을 구분합니다. `active:false` 후보는 현재 후보 수에 포함하지 않고 이전 지원 기록으로 표시합니다. 비활성 사유는 서버가 알려주지 않으므로 마감이나 자격 불충족을 단정하지 않습니다. `schedule_status:upcoming`인 현재 후보는 접수 예정과 시작 전 안내를 표시합니다.

현재 후보는 처음 3개를 보여주고 3개씩 더 볼 수 있습니다. 이전 지원 기록은 펼치기 영역에 보관합니다. 같은 공고의 진행 상태는 모든 분야가 공유하며 `disaster_watch`에서 `disaster_recovery`로 전환되어도 이어집니다. 현재 후보에 있는 공고의 비활성 과거 분야는 데이터는 유지하되 이전 기록에서 중복 표시하지 않습니다.

## 검증

2026-10-08 정보 입력 UI 수정은 Cua 브라우저에서 최초 안내 꺼짐 저장, 접힌 주거 값
보존, `false`/`null` 구별, 저장 오류 뒤 초안·오류 포커스, 안내 켠 뒤 저장, 취소·상담 진입
포커스, 후보 진행 상태·알림 읽음, 320px 일반/쉬운 화면, 영어 전환 중 초안 보존을
확인했습니다. 관련 Node 검사 22개와 운영용 빌드는 통과했습니다. E2E 소스는 새 흐름에
맞게 갱신했으나 이번 수정에서 Playwright CLI는 실행하지 않았습니다. 운영 배포는 하지
