# 유사 복지 서비스에서 얻은 개선 작업 목록

기준일: 2026-10-02. 대상: [K-복지 리서치랩](https://paradise-hero.com/). 적용 제품: 복지나침반.

이 문서는 경쟁 서비스에서 확인한 문제를 복지나침반의 구현·검증 작업으로 바꾼 체크리스트다. 빠른 탐색은 유지하되 정책 금액, 모집 상태, 대상 조건과 공식 링크를 정확하게 안내하는 것을 우선한다. 각 작업에는 현재 구현, 담당 영역, 완료 기준을 기록했다. **체크되지 않은 항목은 남은 작업이며, 이 문서를 작성한 것이 기능 구현 완료를 뜻하지 않는다.**

공개 데스크톱의 홈, 가상 조건 진단, 결과, 상세 링크, 분류·키워드 검색과 개발자 콘솔을 확인했다. 정책 표본 3건은 공식 안내와 대조했다. 모바일, 실제 공공 API 통신, 실제 신청 완료, 전체 정책의 정확성은 검증하지 않았다. 작은 글씨와 연한 설명은 화면상 접근성 위험이며 규격 위반을 확정한 결과가 아니다.

## 우선순위와 현재 구현

- **P0:** 관련 정보를 공개하거나 해당 기능을 활성화하기 전에 확보할 정확성 기준. 잘못된 신청 판단을 일으킬 수 있는 항목이다.
- **P1:** 핵심 이용 흐름의 이해·검색·접근성을 개선하고 현재 보호장치를 검증하는 작업이다.
- **P2:** P0·P1 이후 운영 자동화·알림·측정 기능을 확장할 때 수행한다.

현재 코드에는 공개 승인·비공개 전환과 이력, 공개 개정만 조회하는 경로, 보수적인 신청 날짜 추출, 공식 URL 형식 검사, 원문 인용 검사, 참고 계산, 쉬운 화면과 신청 달력이 있다. 이 기능들을 처음부터 만드는 작업으로 다시 등록하지 않는다. 기능이 있다는 사실과 실제 데이터에서의 운영 검증 완료는 구분한다.

일부 이전 문서는 공개 승인·HTTP 공고 API를 후속이라고 설명하지만, 현재 [공개 관리 코드](../../backend/app/modules/storage/publication.py)와 [공고 API](../../backend/app/api/policies.py)에는 구현이 있다. 실제 추천 API와 자동 알림 발송은 여전히 후속 범위다. 작업 착수 시 해당 기능 코드와 최신 README를 우선 확인한다.

## P0 정확한 정보 공개

### 작업 01 공개 검수와 출처 시각

- [ ] 공개 전 사실 확인과 누락 처리 기준을 확정하고 검수 결과를 남긴다.

**현재:** 공개 승인·비공개·충돌 보호·승인 이력은 구현돼 있다. 공식 링크와 신청기간 누락은 검수 경고로 표시되지만, 경고 자체가 모두 공개를 차단하지는 않는다. 공고 카드의 `date`는 원문 게시일이 아니라 DB 개정 생성일이다.

**할 일:** 정책 금액·대상·적용 연도·신청기간·공식 링크를 원문과 대조하는 검수 항목을 추가한다. 누락이면 차단할 항목과 확인 필요로 공개할 수 있는 항목을 구분한다. 원문 게시일, 원문 변경일, 마지막 원문 확인일, DB 적재일을 혼용하지 않도록 데이터·표시 계약을 정한다.

**완료 기준:** 금액·대상·공식 링크의 필수 검수 누락을 승인 단계에서 탐지한다. 기간 미기재 등 허용한 누락은 화면에 확인 필요로 표시한다. 공개 개정의 검수자·시각·근거·예외 사유를 조회할 수 있다. DB 적재일을 원문 최신성의 근거로 표시하지 않는다.

**참고:** [공개 관리](../../backend/app/modules/storage/publication.py), [카드 생성](../../backend/app/modules/storage/catalog.py), [저장 계약](../../backend/docs/policy-storage.md).

### 작업 02 지원 금액과 기간

- [ ] 금액의 수혜자·지급 주기·기간·상한·지원 형태를 함께 관리한다.

**현재:** 공고의 지원 내용을 요약해 카드·상세에 표시한다. 모든 정책에 대해 위 항목이 구조화되고 상호 검증되는지는 확인하지 않았다.

**할 일:** 개인·가구·기업 중 누구에게 지급하는지, 월·연·회당 금액인지, 몇 개월인지, 최대치인지 조건부 금액인지를 분리한다. 현금·바우처·대출·세액공제를 구분한다. 납입 가능 금액과 정부 지급액을 같은 지원금으로 표시하지 않는다. 정해진 기간을 평생 지급으로 요약하는 오류를 막는다.

**완료 기준:** 부모급여, 월세 지원, 대출, 세액공제처럼 성격이 다른 표본에서 카드·상세·질문 답변의 금액과 기간이 일치한다. 합산 금액은 적용 조건과 계산 근거를 제시한다. 확인되지 않은 기간·금액은 추정값으로 채우지 않는다.

**참고:** [데이터 계약](../../backend/docs/data-contracts.md), [조건 계약](../../backend/app/contracts/conditions.py), [공고 모델](../web/src/features/policies/policyModel.js).

### 작업 03 모집 상태와 마감 시각

- [ ] 모집 상태를 공식 신청기간과 예외 조건에 따라 표시하고 목록·상세·달력을 일치시킨다.

**현재:** 날짜 추출은 다중 기간·잘못된 날짜를 미확인으로 남기며 상시 접수를 구분한다. 날짜 모델은 시간 문구를 읽더라도 결과에 날짜만 반환한다. 신청 달력은 구현돼 있다.

**할 일:** 예정·접수중·마감·상시·확인 필요의 표시 기준을 정한다. 마감 시각과 한국 시간, 예산 소진·선착순·추가 모집·중단 공고를 함께 다룬다. 제도 존속, 기존 수혜자 지급, 신규 접수를 구분한다. 날짜만 알려진 공고의 마감 시각을 임의로 23시 59분으로 확정하지 않는다.

**완료 기준:** 시작 전·접수 기간·마감 후·18시 마감·상시·기간 미기재·다중 모집·조기 종료 표본의 결과가 정해진 규칙과 일치한다. 불명확하면 접수중으로 표시하지 않는다. 카드·상세·달력에서 상태와 시각이 일치한다.

**참고:** [날짜 추출](../../backend/app/modules/storage/application_dates.py), [달력 모델](../web/src/features/calendar/calendarModel.js), [달력 안내](../web/src/features/calendar/readme.md).

### 작업 04 정책과 링크 일치

- [ ] 목록·상세·질문·공식 링크가 같은 정책과 개정을 가리키는지 검증한다.

**현재:** 정책·개정 ID 연결, 답변의 개정 일치 검사와 HTTP(S) URL 형식 검사는 구현돼 있다. 실제 도착 페이지의 정책·기관·연도 일치 여부는 별도 검증이 필요하다. URL 형식이 안전하다는 사실은 해당 정책으로 연결된다는 증거가 아니다.

**할 일:** 정책 ID와 개정 ID를 기준으로 카드·상세·FAQ·출처를 연결한다. 공식 출처와 실제 신청 페이지가 다르면 버튼 이름을 구분한다. 다른 정책의 설명 글이나 기관 홈을 직접 신청 페이지로 안내하지 않는다. 링크 변경·리다이렉트·깨진 링크의 확인 절차를 정한다.

**완료 기준:** 분야별 실제 공고 표본에서 상세 제목·개정·기관·최종 링크를 대조한다. 월세 지원 버튼이 대출 안내로 연결되는 오류를 회귀 시나리오로 재현하고 차단한다. 링크가 없거나 유효하지 않을 때 눌러도 되는 신청 버튼을 만들지 않는다. 기관 홈 연결이라면 그 사실을 명시한다.

**참고:** [상세 화면](../web/src/features/policies/PolicyDetail.jsx), [URL 검사](../web/src/features/policies/policyModel.js), [공고 질문](../../backend/app/modules/assistant/readme.md).

### 작업 05 미확인과 제한 없음

- [ ] 정보 누락을 전체 대상이나 조건 충족으로 바꾸는 기본값을 제거한다.

**현재:** 백엔드 조건 계약은 정보 없음과 명시적인 제한 없음을 구분한다. 백엔드 카드에도 지원 대상 확인 필요 안내가 있다. 프론트엔드 `parsePolicy`는 대상 필드 누락 시 `전체`를 기본값으로 사용한다. 이는 코드상 위험이며 실제 서비스에서 잘못된 공고가 노출됐다는 확인은 아니다.

**할 일:** API 누락·빈 문자열·미확인·명시적 제한 없음을 목록·상세·필터·추천에서 구분한다. 대상 누락은 확인 필요로 표시한다. 지역 누락을 전국, 소득 누락을 제한 없음, 날짜 누락을 상시로 해석하지 않는다.

**완료 기준:** 필드 누락·빈 값·명시적 무제한 표본을 구분한다. 미확인 값으로 신청 가능 또는 전체 대상이라는 결과가 만들어지지 않는다. 미확인 항목이 일반·쉬운 화면과 질문 답변에서도 같은 뜻으로 유지된다.

**참고:** [공고 모델](../web/src/features/policies/policyModel.js), [카드 생성](../../backend/app/modules/storage/catalog.py), [조건 분류](../../backend/docs/condition-classification.md).

### 작업 06 추천과 자격 판단 구분

- [ ] 실제 추천을 활성화하기 전에 관련 공고·조건 비교·최종 자격 판단의 범위를 분리한다.

**현재:** 추천용 정보 입력과 호출자 화면은 있지만 실제 추천 API는 후속이다. 공개 승인을 해도 `matchingEnabled`는 false로 유지한다. 금융 참고 결과와 공고 질문도 전체 자격을 확정하지 않는다.

**할 일:** 빠른 탐색에는 최소 입력을 사용하고 결과마다 일치한 조건·미확인 조건·다음 확인 행동을 표시한다. 거주지·나이·가구·소득·재산·예외 중 확인한 범위를 밝힌다. 금융 비교 하나를 통과했다는 이유로 전체 공고를 신청 가능이라고 표시하지 않는다.

**완료 기준:** 검토된 공고와 사전에 정한 사용자 표본에서 명백한 연령·지역 등 제외 조건을 위반한 추천은 0건이며, 미확인 조건은 추가 확인 필요로 남긴다. 추천 이유는 원문 조건에 대응하고 비교 결과·이유가 API·화면에서 일치한다. 근거 개정을 찾을 수 있다. 추천 서비스 미연결·실패·입력 부족 상태에서 실제 추천이 성공한 것처럼 보이지 않는다. 자격 확정으로 오해되는 문구를 활성화 전에 검토한다.

**참고:** [구현 상태](../../backend/docs/implementation-status.md), [추천 호출자](../web/src/features/assistant/recommendationRepository.js), [개인 안내 계약](../../backend/app/modules/assistant/readme.md).

### 작업 07 기능 설명과 구현 일치

- [ ] 화면·README·발표 자료의 기능 설명을 현재 구현과 실제 검증 범위에 맞춘다.

**현재:** 운영 화면은 실제 공고 API를 사용하며 예시 공고는 테스트에만 존재한다. 일부 이전 문서에는 공고 API·공개 승인 상태와 쉬운 화면 표시 개수에 대한 오래된 설명이 남아 있다.

**할 일:** 실시간·AI 추천·모집중·자동 알림·접근성 검증 같은 표현의 근거를 확인한다. API의 200 응답, DB 연결, 원문 갱신, 모델 실행 성공을 서로 구분한다. 화면·문서에는 사용자가 이해하는 서비스 상태를 표시하고 상세 기술 로그는 운영 문서에서 관리한다. 개발용 문자 인증과 실제 문자 발송도 구분한다.

**완료 기준:** 주요 기능별로 현재 구현·검증 이력·남은 범위를 대응시킬 수 있다. 추천·푸시 미연결을 완료 기능으로 소개하지 않는다. README·기능 문서·발표 자료의 같은 기능 설명이 일치한다. 과거 테스트 결과를 현재 화면의 검증 결과로 재사용하지 않는다.

**참고:** [프로젝트 소개](../../readme.md), [협업 안내](../../CONTRIBUTING.md), [구현 상태](../../backend/docs/implementation-status.md), [쉬운 화면 검증 기록](senior-mode.md).

### 작업 09 조건 입력의 도움

- [ ] 사용자가 기준 용어를 모를 때 계산·설명·모름 선택으로 계속 진행할 수 있게 한다.

**현재:** 금융 계산기에 가구·소득·재산 입력과 미확인 처리가 있다. 경쟁 서비스처럼 중위소득 비율만 직접 고르게 하는 방식을 기본 흐름으로 채택할 필요는 없다.

**할 일:** 중위소득, 소득인정액, 주소지와 생활지역의 차이를 질문 가까이 설명한다. 필요한 공고에서만 추가 정보를 묻고 모름을 0으로 바꾸지 않는다. 이미 구현된 관심사 복수 선택과 모드 전환 시 값 보존을 회귀 검증한다. 비회원 탐색을 위해 불필요한 금융정보 입력이나 저장을 요구하지 않는다.

**완료 기준:** 기준을 모르는 사용자도 탐색 결과와 추가 확인 항목에 도달한다. 0·미입력·모름이 별개로 유지된다. 뒤로 이동·모드 전환 시 입력이 보존된다. 금융정보 저장은 별도의 동의를 유지한다.

**참고:** [계산기 인수인계](finance-calculator.md), [추천 프로필](../web/src/features/profile/readme.md), [금융 모듈](../../backend/app/modules/finance/readme.md).

### 작업 10 검색과 빈 결과

- [ ] 결과 없음·필터 제한·수집 범위·서버 오류를 구분하고 복구 행동을 제공한다.

**현재:** 서버 검색·분야·지역·대상·태그 필터와 페이지 조회가 구현돼 있다. 결과 수·조건 초기화·로딩/오류/빈 결과 구분·이전 요청 취소도 있다. 현재 대상·지역 필터는 문구 포함 검사다. 정책 전체를 수집하는 자동 스케줄러는 후속이다.

**할 일:** 기존 표시·조건 초기화·상태 구분을 회귀 검증한다. 신규 보완으로 수집 범위를 설명하고 실제 검색어와 대상·지역 표현의 일치를 검증한다. 어르신/고령자/65세, 지역 약칭과 행정명 등의 대표 검색어와 기대 결과를 정한다. 빈 결과를 해당 복지가 존재하지 않는다는 뜻으로 표현하지 않는다. 실패를 예시 공고로 채우지 않는다.

**완료 기준:** 정책명·관련 단어·지역+대상 조합·조건 초기화·빈 결과·오류·다음 페이지 시나리오를 확인한다. 초기화하면 검색어와 관련 필터가 실제로 해제된다. 늦게 도착한 이전 검색 결과가 현재 검색을 덮어쓰지 않는다. 빈 결과에 사용자가 실행할 다음 행동이 있다.

**참고:** [공고 검색](../web/src/features/policies/readme.md), [정책 API](../../backend/app/api/policies.py), [서버 검색](../../backend/app/modules/storage/catalog.py).

### 작업 11 공고 질문의 근거

- [ ] 질문 답변의 원문 인용·개정 일치·미기재 정보 처리 보호장치를 회귀 검증한다.

**현재:** FAQ 6개, 공개 개정 기반 자유 질문, 인용 검사와 자격 확정 금지는 구현돼 있다.

**할 일:** 원문에 없는 금액·기간·준비물·대상 조건을 답변이 추정하지 않는지 확인한다. 준비된 답변과 생성된 답변을 실제 경로에 맞게 구분한다. 지원 내용을 설명하는 답변과 사용자의 최종 자격 판단을 구분한다.

**완료 기준:** 미기재 준비물·충돌하는 조건·다른 정책 인용·폐기된 개정·모델 실패의 표본을 검증한다. 근거가 없으면 확인 필요와 공식 확인 경로를 제공한다. 인용이 답변의 숫자·기간·주체를 실제로 뒷받침한다. 오래된 답변이 새 공고 개정으로 오인되지 않는다.

**참고:** [개인 안내 모듈](../../backend/app/modules/assistant/readme.md), [FAQ 구현](../../backend/app/modules/assistant/faq.py), [웹 질문 화면](../web/src/features/assistant/PolicyQuestion.jsx).

### 작업 12 금융 계산의 설명

- [ ] 참고 계산의 적용 연도·산식·입력 단위·미확인 항목을 결과와 함께 검증한다.

**현재:** 서버 참고 계산과 회원 원입력 저장·조회 시 재계산이 있다. 결과는 전체 신청 자격 확정이 아니다.

**할 일:** 입력 만원과 서버 원 단위 변환, 가구원 수, 세전·경비 기준, 사업별 재산 산식 차이를 설명한다. 계산한 항목과 지원하지 않는 예외를 구분한다. 규칙이 바뀌면 저장 입력으로 재계산한 결과의 기준 연도를 표시한다.

**완료 기준:** 소득 0·미확인·가구 변경·소득 경계값·재산/차량 예외 표본의 결과와 안내를 검증한다. 결과 수치를 재현할 수 있고 원문 기준을 찾을 수 있다. 일부 항목 미확인 결과를 전체 조건 충족으로 표시하지 않는다.

**참고:** [공식 산정 규칙](../../backend/docs/financial-rules.md), [금융 저장 계약](../../backend/app/modules/finance/readme.md), [계산 결과 화면](../web/src/features/finance/FinanceResult.jsx).

### 작업 13 쉬운 화면과 접근성

- [ ] 핵심 탐색·상세·입력·질문 흐름을 키보드와 화면낭독기로 검증한다.

**현재:** 쉬운 화면, 한 열에 공고 3개 표시, 입력·필터 보존과 상세창 초점 복귀가 있다. 전체 대비 상태와 실제 고령 사용자·화면낭독기 검증은 남아 있다.

**할 일:** 기존 [쉬운 화면 설계](senior-mode.md)의 글자·대비·누르는 영역 기준을 화면별로 확인한다. 선택·오류·비활성·초점 상태를 포함한다. 중요한 조건·고지·오류를 작은 보조 글씨나 색상만으로 전달하지 않는다. 대상 사용자와 핵심 과업을 수행하고 막힌 지점을 기록한다.

**완료 기준:** 마우스 없이 탐색·필터·상세 열기/닫기·입력 오류 복구·공식 링크 이동이 가능하다. 버튼 이름과 초점 위치가 이해 가능하며 상태 변화가 전달된다. 대상 사용자가 검색 → 대상·기간 이해 → 공식 공고 열기 과업을 수행한 결과와 막힌 지점의 처리 결과를 남긴다. 자동 검사·개발자 검토·사용자 참여 평가를 따로 기록하고 인증 완료로 확대하지 않는다.

**참고:** [쉬운 화면 기준과 남은 검증](senior-mode.md), [공통 UI](../web/src/shared/ui/readme.md).

### 작업 14 모바일과 확대 화면

- [ ] 좁은 화면·200% 확대·긴 공고·오류 상태에서 정보와 행동이 가려지지 않는지 확인한다.

**현재:** 일부 주요 화면의 320px 폭 검증 이력이 있다. 해당 기록이 모든 페이지와 모든 상태를 검증한 것은 아니다.

**할 일:** 320px·390px·768px·데스크톱과 200% 확대에서 목록·상세·달력·계산기·질문·로그인 흐름을 확인한다. 긴 제목·긴 금액·긴 URL·여러 확인 항목·오류 메시지와 모바일 키보드를 포함한다. 고정 메뉴가 제목·마감·버튼을 가리지 않게 한다.

**완료 기준:** 중요한 정보가 잘리거나 의도하지 않은 가로 스크롤이 생기지 않는다. 모바일 키보드가 떠도 입력·오류·주 행동을 이용할 수 있다. 기본↔쉬운 전환에서 입력·검색 조건이 유지된다. 모바일 웹 결과를 실제 Android/iOS 앱 검증 결과로 대신하지 않는다.

**참고:** [쉬운 화면 검증 범위](senior-mode.md), [달력 화면](../web/src/features/calendar/readme.md), [모바일 이식 범위](mobile-migration.md).

### 작업 15 오류 정정 절차

- [ ] 잘못된 정책 정보의 접수·임시 비공개·수정 검수·재공개 절차를 정한다.

**현재:** 개정 저장, 비공개 전환, 공개 이력은 구현돼 있다. 사용자 오류 제보 접수와 처리 상태 안내는 별도 확인·설계가 필요하다.

**할 일:** 제보에 정책 ID·문제 항목·근거 링크를 연결한다. 신청 판단에 영향을 주는 오류는 우선 확인하고 필요하면 비공개 처리한다. 원본 개정을 덮어쓰지 않고 수정 개정을 검수한다. 공개 여부와 신청 자격 판정 활성화는 계속 분리한다.

**완료 기준:** 금액·마감·잘못된 링크 오류 표본 하나를 접수부터 재공개까지 처리할 수 있다. 수정 전후 값·처리 사유·개정을 조회할 수 있다. 정정된 개정이 목록·상세·달력·질문에 반영된다. 제보에 불필요한 개인정보를 요구하지 않는다.

**참고:** [공개 관리](../../backend/app/modules/storage/publication.py), [공고 저장](../../backend/docs/policy-storage.md).

### 작업 16 저장 공고의 최신 정보

- [ ] 저장 공고를 다시 열 때 최신 공개 개정과 현재 공개 상태를 확인한다.

**현재:** 공고 저장은 현재 브라우저에 공고 객체를 보관하는 방식이다. 저장 당시 정보가 남을 수 있으며 계정·기기 간 동기화 완료를 뜻하지 않는다. 최신 공개 상세 조회 API는 있다.

**할 일:** 정책 ID로 최신 공개 개정을 조회하고 저장 당시 개정과 비교한다. 기간·금액·공식 링크 변경과 공개 취소를 표시한다. 최신 조회에 실패하면 기존 정보를 최신이라고 보여주지 않고 마지막 확인 시각과 확인 필요를 안내한다. 저장 위치 설명도 유지한다.

**완료 기준:** 저장 후 제목·기간·링크 변경, 개정 교체, 공개 취소, API 실패 시나리오를 확인한다. 질문은 현재 표시한 개정을 기준으로 실행된다. 조회 실패를 공고 삭제로 오인하지 않으며 저장 목록에서 과거 정보를 계속 신청 가능한 것처럼 안내하지 않는다.

**선행:** 작업 03·04. **참고:** [브라우저 저장과 상세 연결](../web/src/app/App.jsx), [최신 공고 API](../../backend/app/api/policies.py).

## P2 운영 기능 확장

### 작업 17 원문 갱신 운영

- [ ] 자동 수집을 도입할 때 변경 감지·갱신 실패·검수 대기를 관리한다.

**현재:** 수집·개정 저장은 있으며 자동 전체 수집·스케줄러는 후속이다.

**할 일:** 정책 종류와 모집 일정에 맞는 갱신 주기를 정한다. 원문 내용 변경과 접수 종료를 감지하고 검수 대기열에 연결한다. 재시도·실패 이력과 마지막 원문 확인 시각을 관리한다. 갱신 실패를 성공으로 표시하거나 임의의 최신 날짜로 바꾸지 않는다.

**완료 기준:** 정상 갱신·원문 변경·기관 오류·중복 수집·중단 공고를 확인한다. 기존 개정과 검수 이력이 유지되고 실제 확인 시각을 조회할 수 있다. 데이터가 오래됐을 때 사용자 안내와 운영자 조치 기준이 정해져 있다.

**선행:** 작업 01·03·15. **참고:** [수집 모듈](../../backend/app/modules/collectors/readme.md), [파이프라인](../../backend/app/modules/pipeline/readme.md).

### 작업 18 알림의 실제 연결

- [ ] 알림은 실제 발송·동의·취소까지 확인한 범위만 제공한다.

**현재:** 공고 저장은 브라우저 기준이다. 웹 알림은 미구현이며 모바일 서버의 동의·기기 등록·메시지 준비와 실제 자동 발송은 다른 단계다.

**할 일:** 계정 동기화와 알림은 별도 확장으로 설계한다. 마감 시각·정정 개정·권한 거부·만료 토큰·중복 발송·수신 취소를 다룬다. 알림 허용을 탐색의 필수 조건으로 만들지 않는다.

**완료 기준:** 기존 브라우저 저장을 운영 푸시처럼 소개하지 않는다. 알림 기능을 활성화할 때 실제 기기에서 수신·수신 취소·마감 변경·중복 방지·전송 실패를 검증한다. 동의나 기기 등록 성공만으로 발송 완료라고 표시하지 않는다.

**선행:** 작업 03·07·16·17. **참고:** [웹 알림 범위](../web/src/features/notifications/readme.md), [서버 알림 범위](../../backend/app/modules/notifications/readme.md).

### 작업 19 검증 가능한 지표

- [ ] 조회수·예산 상태·추천 품질 지표를 도입할 때 출처·계산 방식·기준 시각을 정한다.

**현재:** 경쟁 서비스 화면에는 조회수·예산소진율이 있으나 이번 감사에서 산식·원천 데이터를 확인하지 못했다. 복지나침반에 같은 지표를 반드시 추가해야 한다는 요구는 아니다.

**할 일:** 검증할 수 없는 예산소진율·당첨 가능성·사회적 증거 수치를 표시하지 않는다. 운영 개선에는 검색 실패율·공식 안내 클릭·정보 오류율·정정 처리·갱신 지연·이용 과업 성공 등을 필요한 범위에서 측정한다. 공식 링크 클릭을 신청 완료로 집계하지 않는다.

**완료 기준:** 노출하는 지표마다 실제 데이터·계산 방법·기간을 설명할 수 있다. 근거 없는 지표는 숨긴다. 개인별 금융·건강 등 민감한 내용을 지표 기록에 포함하지 않는다. 지표가 없다는 이유로 임의 수치를 만들지 않는다.

**선행:** 작업 07·10·15. **참고:** [지표 모듈의 현재 범위](../../backend/app/modules/metrics/readme.md).
