# 소득·재산 계산기와 화면 개선 인수인계

기준일: 2026-10-06. 이 문서는 계산기의 기능, 저장 방식, 실행 방법과 후속 연결 지점을 정리합니다. 실제 산식·공식 출처·미지원 특례는 [백엔드 산정 기준](../../backend/docs/financial-rules.md)을 기준으로 확인합니다.

## 가족·지인 지원 내역과 부분 참고액 (2026-10-08)

생계급여는 가구 전체의 최근 12개월 월별 지원금 합계·횟수·지원자 관계·사용 용도를 받아 일반 생활비 지원을 계산합니다. 현재 월 지원금은 단순 소득 합계에만 사용하며 생계급여 반영액과 중복 합산하지 않습니다. 지원받음 선택 시에만 월별 내역을 표시하고, 매달 같은 지원을 12개월 내내 받았다면 첫 달 금액·횟수를 반복 적용할 수 있습니다. 미입력 달은 사용자가 지원이 없었다고 확인한 경우에만 0으로 처리합니다.

정보가 부족하거나 지정 용도·특수 지원 관계·비정기 큰 지원·기간 경과가 있으면 지원금 미반영 참고액과 확인 사항을 표시합니다. 쉬운 화면에서도 미반영 안내를 항상 표시하며, ‘기준 이내’ 대신 ‘지원금 반영 후 비교 필요’로 표시합니다. 원입력은 `private_transfer_history`에 저장하고, 지난 기준 월은 이번 달의 12개월 내역으로 다시 입력해야 합니다. 웹·모바일은 공통 입력 모델과 질문을 사용합니다.

검증: 백엔드 소득·저장 API 127개, 웹 단위 검사 181개, 모바일 금융 검사 11개 통과. 모바일 타입 검사·린트와 웹 빌드 통과. 실제 계산 API를 이용한 데스크톱·휴대폰 화면 4개에서 미확인 지원금의 비교 보류와 정기 생활비 지원의 자동 반영을 확인했습니다.

## 가구 정보 문구 정리 (2026-10-08)

- ‘현재 수급 상태’를 ‘지원 대상 구분’으로, ‘기초생활수급자’를 ‘국민기초생활수급자’로 변경했습니다. ‘차상위계층’, ‘해당 없음’, ‘모름’은 유지합니다. [복지로 저소득층 교육지원 안내](https://www.bokjiro.go.kr/ssis-tbu/twataa/wlfareInfo/moveTWAT52011M.do?wlfareInfoId=WLF00003702&wlfareInfoReldBztpCd=01)의 지원대상 명칭을 참고했습니다.
- 가구원 범위 확인·추가 혜택 확인 체크박스 아래의 긴 보조 안내 두 개를 제거했습니다. 체크박스와 ‘선택 · 필수 아님’ 표시는 유지합니다.
- 공통 모델과 다국어 사전에 반영했습니다. 저장·전송 값(`unknown`, `none`, `near_poor`, `basic`)과 계산 동작은 유지합니다.

## 회원 정보 자동 입력과 초안 우선순위

2026-10-06: 회원으로 빠른 계산기·상세 계산기·내 정보에 들어오면 공통 `useFinancePrefill`에서 `GET /v1/finance/profile`을 조회합니다. 계정별 결과는 앱 메모리에서 공유하므로 화면을 옮길 때 같은 정보를 다시 입력하지 않아도 됩니다. 저장은 기존처럼 별도 동의와 저장 버튼으로만 실행합니다.

- 저장 정보가 있으면 빠른 화면의 가구원 수와 확인된 월소득을 채우고 상세 화면은 입력 확인부터 시작합니다. 최초 상세 입력에서 회원 조회를 기다리는 동안 로딩 상태를 제공합니다.
- 저장 정보가 없으면 최초 단계별 입력을 제공합니다. 회원의 확정 만 나이와 계산 지역으로 구분 가능한 거주 지역을 미리 채우고 다른 가구원의 나이·소득은 비워 둡니다. 연령대나 가족 동거 여부로 정확한 나이·가구원 수를 추정하지 않습니다.
- 직접 수정한 빠른 화면 값과 작성 중인 상세 초안이 자동 조회 결과보다 우선합니다. 비회원으로 작성하다 로그인해도 같은 실행 중 초안을 이어 쓰며, 저장본으로 바꾸려면 ‘저장한 정보 불러오기’를 선택할 수 있습니다.
- 조회 중·정상 미저장 응답·조회 실패를 구분하고 재시도를 제공합니다. 실패 응답으로 현재 입력을 초기화하지 않습니다. 내 정보에서는 미저장 상세 초안을 ‘작성 중’으로 표시합니다.
- 계정 전환·로그아웃·페이지 이탈 시 요청을 취소하고 이전 응답을 무시합니다. 저장·명시적 불러오기는 공유 캐시를 갱신하고 삭제는 캐시와 진행 중 조회를 무효화해 늦은 응답이 삭제된 정보를 되살리지 않게 합니다.
- 빠른 화면에서 선택한 실제 가구원 수는 상세 입력에서도 이어 씁니다. 가구 전체 월소득은 개인별 소득으로 나누거나 복사하지 않습니다. 상세 소득 합계는 모든 금액을 알고 양수 근로·사업소득의 입력 기준도 확인된 경우에만 빠른 화면에 채웁니다.
- 상세 계산기와 내 정보에서 아이디 로그인을 거치면 허용된 `return` 경로로 원래 화면에 돌아옵니다. 신규 가입의 맞춤 정보 설정과 카카오 기존 회원 콜백의 홈 이동은 유지합니다.

## 입력과 저장

빠른 확인은 [보건복지부 2026년 공식 기준](https://www.mohw.go.kr/menu.es?mid=a10708010900)을 사용합니다(2026-10-06 확인). 가구원 수만으로 기준 금액을 표시하고, 월소득을 입력한 경우에만 비율을 표시합니다. 빈칸은 미입력, 0은 실제 소득 없음으로 구분합니다. 소득 공제·재산 환산을 반영하는 소득인정액은 상세 계산에서 확인합니다.

- 가구원 수는 1~6명과 ‘7명 이상’으로 먼저 묶습니다. 빠른 계산기는 ‘7명 이상’을 선택하면 바로 실제 인원을 직접 입력합니다. 상세 계산기는 7~11명은 추가 선택지, 12명 이상은 직접 입력으로 실제 인원을 받습니다. 자녀 수는 없음·1명·2명·‘3명 이상’으로 먼저 묶고 3~8명은 선택지, 9명 이상은 직접 입력을 제공합니다. 자녀 수는 가구원 수를 넘을 수 없습니다. 묶음 선택을 기준 인원으로 확정하지 않으며 계산·저장에는 정확한 인원을 사용합니다. 큰 인원의 기존 저장값도 축소하지 않습니다.
- 금액 입력은 **만원 단위**입니다. 보증금 500만 원은 `500`으로 입력하며 소득·재산·부채·차량 가액에 같은 단위를 적용합니다. 입력 아래 원 단위 환산값을 표시합니다. 소수점 넷째 자리(1원)까지 보존하고, API·DB·계산 결과는 기존 원 단위 계약을 유지합니다.
- 소득·재산 항목에서 ‘있어요/금액 입력’을 선택하면 금액을 입력해야 다음 단계로 갈 수 있습니다. 금액을 모르면 ‘모르겠어요’, 없으면 ‘없어요 (0원)’를 선택합니다. 빈 금액을 조용히 미입력으로 보내 계산 합계가 ‘확인 필요’가 되는 일을 막습니다.
- 입력 항목은 가구원별 나이·근로/사업/기타/사적이전 소득·공제 유형, 소유 주택·전월세 보증금·일반/금융 재산, 부채 종류, 차량별 가액·종류·용도·배기량·차령·정원입니다.
- 상세 입력에서 산식에 쓰이지 않는 직업군 질문을 제거했습니다. 실제 계산에 필요한 소득 종류·금액·입력 기준과 나이·공제 유형을 묻습니다. 기존 저장 데이터의 `members[].occupation`은 호환성을 위해 보존하고 누락값은 `unknown`으로 읽습니다.
- 근로소득은 세전 기준인지, 사업소득은 필요경비 차감 후인지 별도로 기록합니다. 실수령액·매출액만 알면 그대로 입력하고 해당 기준을 선택할 수 있지만, 서버가 세전 소득으로 임의 환산하거나 소득 비교를 확정하지 않습니다. 양수 소득일 때만 금액 기준 질문을 표시합니다.
- 양수 근로·사업소득을 입력한 경우 해당 금액의 기준(세전/실수령액 또는 경비 차감 후/매출액)도 반드시 선택해야 다음 단계로 갈 수 있습니다. 기준을 확인할 수 없으면 해당 소득 금액을 ‘모르겠어요’로 남길 수 있습니다. 기존 저장값의 미확인 기준은 그대로 보존하며 사업별 계산은 추가 확인으로 남습니다.
- 차량은 본인·가구원 단독 명의인지, 공동 명의·리스·회사 차량인지 구분합니다. 등록증의 영업용/비영업용과 실제 수입 활동에 쓰는지는 별도 항목입니다. 가액의 출처와 저공해차 보조금 여부도 기록하고, 확인되지 않은 예외는 추가 확인으로 남깁니다.
- 근로소득의 공적자료·비과세 예외와 기간, 사업소득의 소득세·개인지방소득세 차감 전 원칙, 실제 LH 공고의 차량 기준은 [입력 근거 조사](../../backend/docs/finance-input-evidence-2026.md)에 정리했습니다. 모든 사업의 조회 기간을 최근 3개월로 통일하지 않습니다.
- 새로 추가한 소득·차량 기준 필드는 기존 저장 JSON에서 `unknown`으로 읽습니다. 과거 금액을 세전 또는 공적 차량가액으로 추정하지 않으며 다시 확인해야 합니다. 원입력 스키마는 추가 선택 필드가 호환되는 버전 1을 유지합니다.
- **없는 금액은 `0`, 모르는 금액은 `null`**입니다. 서버는 원 단위 정수와 가구원·차량 목록의 일관성을 검사합니다.
- 입력한 월 소득 합계는 모든 소득 금액이 확인되면 표시합니다. 중위소득 비율은 그 합계를 기준 중위소득과 나눈 단순 참고값으로, 세후 급여·매출을 입력한 경우 실제 세전·경비 차감 후 기준과 다를 수 있습니다. 사업별 산식은 해당 기준을 확인하기 전까지 별도로 ‘확인 필요’로 표시합니다. 소득 항목에 `null`이 있으면 일부 금액만 합산하지 않고 전체 합계를 ‘확인 필요’로 표시합니다.
- 가구원별 ‘소득이 모두 없어요’는 사용자가 선택했을 때만 근로·사업·기타·사적이전 소득 네 항목을 0으로 설정합니다. 나이·직업·학생 여부로 소득 없음을 추정하지 않습니다. 나이·공제 유형만 바꾸면 빠른 화면에서 직접 작성한 월소득을 보존합니다.
- 비회원 입력은 계산 요청에 사용하며 DB에 저장하지 않습니다. 금융정보는 `localStorage`와 `sessionStorage`에 기록하지 않습니다.
- 입력 중 초안·현재 단계·결과는 앱 메모리에 보관해 다른 메뉴를 방문해도 이어서 작성할 수 있습니다. 계산·추천용 원자료와 초안은 분리하며 입력 변경 시 이전 결과와 추천 선택을 해제합니다. 새로고침하면 저장하지 않은 금융정보가 사라집니다.
- 최초 입력은 기본/쉬운 화면 모두 상단 진행 표시와 일치하는 6단계로 진행하고 입력 확인·결과에서 전체 수정 화면을 엽니다. 가구원별 소득은 소득 단계에, 차량 보유 여부와 차량별 상세는 차량 단계에 함께 표시합니다. 쉬운 화면은 ‘금액 입력·없음·모름’을 선택 상자로 구분합니다. 차량 없음/모름이면 상세 질문을 생략합니다. 가구원 수 감소·차량 여부 변경으로 제외한 값은 같은 실행 중 복구할 수 있지만 계산 API에는 포함하지 않습니다.
- 비회원이 계산 후 로그인하면 해당 실행 중 입력을 이어서 사용할 수 있습니다. 계정 저장본은 자동 조회하되 미저장 초안이나 직접 수정한 값을 덮어쓰지 않으며 저장본으로 교체할 때는 명시적 불러오기를 사용합니다.
- 회원은 세션으로 확인한 본인 계정의 최신 원입력만 저장합니다. 계산 결과는 보관하지 않고 조회할 때 현재 서버 규칙으로 다시 계산합니다.
- 계정 전환·로그아웃은 이전 회원의 금융 메모리를 초기화합니다. 회원 금융정보 삭제는 기본 추천 프로필·저장 공고·계정 삭제와 별개입니다.
- 저장·삭제 응답을 기다리는 중 메뉴를 이동해도 계정 요청은 완료하고 공통 정보를 갱신합니다. 그 사이 새로 수정한 입력은 유지하며, 계정이 바뀌면 이전 계정의 결과를 현재 입력에 반영하지 않습니다. 미확인 소득을 다시 불러오면 과거에 자동 입력한 합계는 비우고 직접 작성한 빠른 월소득은 보존합니다.

기존 `#profile`의 지역·관심 분야와 기억하기 옵션은 별도 기능입니다. 이 브라우저 프로필을 회원 금융정보로 오인하지 않도록 저장 경계를 유지합니다.

## 프론트와 서버 연결

| 경로                              | 인증·입력                             | 결과                                                        |
| --------------------------------- | ------------------------------------- | ----------------------------------------------------------- |
| `GET /v1/finance/rules`           | 비회원 가능                           | 지원 연도·규칙 버전·공식 출처                               |
| `POST /v1/finance/calculate`      | 비회원 가능, `{profile, allow_approximation?}` | 중위소득·자산·사업별 참고 계산. 근사 옵션은 명시적 선택 시만 적용 |
| `GET /v1/finance/profile`         | 회원 세션                             | `{profile, calculation, updated_at}`, 미저장 시 모두 `null` |
| `POST /v1/finance/profile`        | 회원 세션, `{profile, consent: true}` | 저장한 원입력과 서버 재계산 결과                            |
| `POST /v1/finance/profile/delete` | 회원 세션, `{}`                       | `{deleted: true}`                                           |

공개 계산은 인증 쿠키를 전송하지 않습니다. 회원 요청은 쿠키를 포함하며 POST에는 `X-Auth-Request: 1`이 필요합니다. 응답은 캐시하지 않고, 실패 시 예시 계산으로 바꾸지 않습니다. 금융 API는 공고의 `demo/api` 설정과 관계없이 실제 서버를 사용합니다.

상세 타입·오류는 [입력 계약](../../backend/app/contracts/finance.py), [금융 모듈](../../backend/app/modules/finance/readme.md), [루트 API 관리대장](../../api-management.md)을 참고합니다. Android/iOS도 같은 서버 계약을 사용할 수 있지만 네이티브 화면·인증 저장소는 아직 구현하지 않았습니다.

## 로컬 실행과 운영 준비

1. [백엔드 실행 안내](../../backend/readme.md)에 따라 API를 실행합니다. 공개 계산은 DB·인증을 끈 상태에서도 동작합니다.
2. 회원 저장은 기존 인증 설정이 필요합니다. 개발·테스트에서 `DB_ENABLED=false`이면 인증용 SQLite를 사용하고 회원의 첫 금융 요청에서 테이블을 추가합니다.
3. 웹에서 `npm ci`, `npm run dev`를 실행한 뒤 `http://127.0.0.1:5173/#calculator`를 엽니다. 기본 `/api` 프록시는 `http://127.0.0.1:8000`에 연결합니다. 별도 서버 주소는 `API_PROXY_TARGET`으로 지정하고 Vite를 재시작합니다.
4. MySQL을 사용할 때는 대상 DB 설정을 확인하고 [금융 모듈의 초기화 명령](../../backend/app/modules/finance/readme.md#db-초기화)을 명시적으로 실행합니다. HTTP 요청에서는 MySQL 테이블을 자동으로 만들지 않습니다. 기존 정책 SQL을 다시 실행할 필요는 없습니다.
5. 운영은 HTTPS와 같은 사이트 API 프록시, 인증 쿠키 설정, 인증·금융 테이블, 실제 SMS 공급자를 준비해야 합니다. 자세한 절차는 [배포 문서](deployment.md)에 있습니다. 이번 작업에서 운영 MySQL에 적용하지 않았습니다.

## 실제 공고 추천으로 연결할 부분

현재 공고·추천 서버 API와 정책 저장소는 미구현입니다. 예시 공고를 금융정보에 맞는 실제 추천으로 표현하지 않습니다.

후속 서버 작업은 다음 순서로 연결합니다.

1. 공고 원문에서 적용 연도, 심사 가구 범위, 소득 기준, 재산·차량 포함 여부, 부채 처리, 한도와 예외를 구조화하고 검토합니다.
2. 서버가 검토한 `PolicyFinancialCriteria`만 `evaluate_policy(profile, criteria)`에 전달합니다. 사용자가 보낸 `reviewed`나 LLM의 추정만으로 규칙을 승인하지 않습니다.
3. 같은 원입력에서 공고별로 독립 계산합니다. 생계급여의 소득인정액을 국민임대 소득으로 재사용하지 않습니다. 미지원 조건과 누락은 확인 필요 상태로 유지합니다.
4. 추천 서비스가 계산 근거와 확인할 사항을 설명하도록 연결합니다. 함수의 `eligibility_decision`은 현재 항상 `null`이며 수급·입주 자격을 확정하지 않습니다.

프론트는 사용자가 ‘관련 공고 살펴보기’를 선택한 뒤에만 추천 요청에 `financialProfile`을 포함합니다. 선택은 현재 실행 중 유지되며 새 계산·불러오기·저장·계정 전환 등으로 해제됩니다. 전체 요청 계약은 [추천 API 제안](service-contract.md)을 참고하세요.
