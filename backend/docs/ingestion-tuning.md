# 최초 대량 수집과 평상시 수집 튜닝

2026-10-06 구현. 관리자 **수집 실행 → 자동 수집 프리셋 → 프리셋 적용·저장**에서
두 운영 모드를 선택한다. 설정 저장은 실행을 시작하지 않는다. 등록된 Windows 작업은
10분마다 `.env`를 다시 읽으므로 다음 회차부터 반영된다. 등록 전에는 **자동 수집 등록**을
사용한다. 실제 공공 API·MySQL·유료 모델 호출과 작업 등록은 이번 개발 검증에서 실행하지 않았다.

## 프리셋의 예산

| 항목 | 최초 대량 수집 (`bootstrap`) | 평상시 지속 수집 (`steady`) |
| --- | --- | --- |
| 목록 페이지 크기 | 100건 | 100건 |
| 회차 목록 조회 | 최대 30페이지 | 최대 8페이지 |
| 회차 데이터 요청 | 최대 80회 | 최대 24회 |
| 회차 상세·분석 작업 | 최대 100개 | 최대 24개 |
| 회차 AI 호출 | 최대 12회 | 최대 4회 |
| 하루 AI 호출 | 최대 120회 | 최대 40회 |
| 회차 보고된 토큰 | 200,000 | 60,000 |
| 회차 시간 | 540초 | 540초 |
| AI 묶음 | 최대 4건 / 전체 프롬프트 24,000글자 | 동일 |
| 기본 / 검증 실패 모델 | GPT-6 Luna low / GPT-6.1 Sol medium | 동일 |
| HTTP 간격 | 최소 1초 | 최소 1초 |
| 전체 목록 재확인 / 상세 재확인 | 6시간 / 24시간 | 동일 |
| 대기열 | 최대 50,000작업 | 동일 |
| 외부 AI 검색 | 끔 | 끔 |

숫자는 검증 가능한 시작 예산이며 이 계정·장비에서 측정한 최적값은 아니다. 페이지 수는
공고 완료 건수와 다르고, 상세 조회·재시도·fallback도 호출 한도에 포함된다. 시간과 일일
한도에 먼저 도달하면 다음 회차에서 이어간다. 토큰은 이미 완료된 호출의 보고 사용량으로
후속 호출을 멈추는 soft limit이다. 한 호출의 출력·비용을 정확히 고정하는 상한은 아니다.

공공 API의 **일일 한도와 키는 프리셋 적용 시 변경하지 않는다**. 기존 기본 한도(복지로
60회, 정부24 200회)가 낮으면 최초 확보도 여러 날짜에 걸친다. 공급자 계정의 허용량을 확인한
운영자가 서버 설정에서 조정한다. 하루 AI 호출도 Codex 구독의 잔여 사용량과 동일한 단위가
아니며 별도 조정이 필요하다. 신규 모델의 접근 가능 여부는 로그인·계정·조직 설정에 따른다.

## 처리 순서와 재개

최초 모드는 AI 대기열에 앞서 API 원문·상세를 확보한다. 한 회차에서 공급자/엔드포인트를
번갈아 조회하여 실제 페이지 예산을 소진한다. 이전 구현은 엔드포인트마다 한 페이지만
조회해 큰 페이지 예산을 충분히 쓰지 못했다. 각 페이지의 원문/대기열/다음 cursor는 함께
커밋한다. 대기열이 가득 차면 분석을 잠시 진행해 공간을 만든다.

현재 설정에 등록된 공급자의 전체 목록과 상세 작업이 끝나면 분석으로 넘어간다. 분석 대기열도
처리 종료되면 MySQL `bootstrap.complete`를 저장하고 다음 회차부터 평상시 예산으로
전환한다. 실패한 작업은 기존 실패 목록에 남으며 무한 유료 재시도를 하지 않는다. 자동
전환은 데이터 처리 종료이며 모든 공고가 검증 성공했다는 뜻은 아니다. 저장된 기본/대체 모델과
묶음 크기의 사용자 조정은 전환 시 보존한다.

평상시 모드는 원문을 확인한 뒤 상세와 분석을 처리한다. AI 예산이 0이거나 일일 AI 한도가
소진되어도 API 원문 확인이 먼저 진행된다. 내용 해시가 같고 처리 signature도 같으면
기존 작업·결과를 재사용한다. 모델·프롬프트·코드가 바뀌면 기존 대기 원문에 새 작업 identity를
만들어 새 버전으로 처리한다. 완료된 결과·중간 검증 결과는 재시작 뒤에도 유지한다.

**기존 공고 전체 연결**은 작은 100건 DB 트랜잭션을 끝까지 반복한다. 매 묶음마다 worker
lease를 갱신하고 화면에 확인/연결 건수를 보낸다. API·AI 호출은 없으며 중단 후 재실행하면
저장 cursor에서 이어간다. CLI에서도 `seed-existing --all`로 사용할 수 있다.

## AI 입력과 출력 최적화

- 요약·분류와 코드로 해결하지 못한 조건 추출을 한 CLI 호출에서 처리한다. 최대 4개 공고가
  지시문과 JSON 스키마를 공유한다. 코드 규칙으로 완료된 공고는 요약만 요청한다.
- 입력에는 모든 비어 있지 않은 원문 필드를 보존한다. hash/빈 필드/전송용 URL을 제거한다.
  제목·URL·중첩 policy_key는 서버에서 채우므로 모델이 반복 출력하지 않는다.
- 묶음 전체 프롬프트의 글자 한도를 계산해 다음 공고를 넣을지 결정한다. 긴 단일 원문은
  기존 단건 경로로 처리한다. 본문을 임의 잘라 수치·예외·인용을 잃지 않는다.
- 공고별 schema·원문 인용·조건/그룹·정규화를 검증한다. 묶음 결과는 순서가 아닌 policy_key로
  매칭하며 누락/중복 identity도 실패로 본다. 성공한 이웃은 먼저 checkpoint에 보존한다.
- 검증 실패한 공고만 Sol medium으로 한 번 재처리한다. 이미 검증된 요약은 다시 생성하지
  않는다. 인증·네트워크·시간 초과는 상위 모델 호출로 확대하지 않는다.
- `--ephemeral`, 도구/검색/스킬 비활성, 고정 지시문·스키마, 작은 공고 묶음을 사용한다.
  긴 resume 대화에 과거 모든 공고를 계속 누적하지 않는다.
- shared CLI usage는 회차 예산에 한 번만 합산한다. 작업별 시도에는 batch_id와 공유 사용량
  표시를 남긴다. last_tick에 입력/캐시 입력/출력/추론 토큰을 따로 기록한다.

4건 합성 입력의 앱 프롬프트 비교는 단건 요약+조건 8회 **27,828글자**, 통합 묶음 1회
**7,605글자**로 72.7% 감소했다. CLI가 주입하는 context, tokenizer와 출력은 제외한 값이다.
실제 토큰·구독 사용량·비용 절감률이나 실제 복지 공고 정확도의 실측값으로 해석하지 않는다.
규칙으로 조건이 이미 끝나는 공고는 기존에도 요약만 호출하므로 단건 4회와 비교해야 한다.

## 조사 근거와 적용 범위

1. [공식 Codex 모델 안내](https://learn.chatgpt.com/docs/models): Luna를 고용량 요약·추출·분류에,
   Sol을 복잡한 작업에 권장한다. Luna의 일반 출발값은 High이나 빠르고 범위가 명확한 작업은
   Low가 가능하며, 낮은 설정의 대표 작업 평가를 권고한다. 여기서는 코드 선처리와 근거
   검증을 붙인 low를 시작값으로 사용한다. 오류가 많으면 사용자 설정으로 올린다.
2. [GPT-6 사용 안내](https://developers.openai.com/api/docs/guides/latest-model): Luna의
   고용량 처리 역할과 Sol의 품질/비용 절충, 지원되는 추론 설정을 확인했다. Astra/Max/Ultra는
   이 정형 추출 기본 경로의 비용 대비 이점이 입증되지 않아 기본값으로 채택하지 않았다.
   GPT-5.6 Luna/Terra는 계속 설정 가능한 기존 모델이며 전용 복지 공고 비교 실험이 없다.
3. [비대화형 Codex](https://learn.chatgpt.com/docs/non-interactive-mode): `codex exec`의
   `--output-schema`, JSON 이벤트·usage를 이용한다. API Batch/Flex는 별도 API 기능이므로
   CLI 구독 경로의 할인이나 기능으로 간주하지 않았다.
4. [공식 Prompt Caching 201](https://developers.openai.com/cookbook/examples/prompt_caching_201):
   지시문·스키마를 앞에 고정하고 변하는 입력을 뒤에 배치하는 방식이 캐시 재사용에 유리하다.
   CLI에서는 실제 cache hit를 보장하거나 API의 캐시 옵션을 임의 전달하지 않는다.
5. [EMNLP 2023 Batch Prompting 연구](https://aclanthology.org/2023.emnlp-industry.74/):
   10개 QA/추론 데이터셋에서 묶음 처리의 token/time 효율을 평가했다. 오래된 모델·다른
   업무의 결과라 복지 공고에 절감률을 그대로 적용하지 않는다. 작은 묶음부터 검증하는 근거다.
6. [Codex 사용자 비교 실험 #35050](https://github.com/openai/codex/issues/35050):
   사용자가 독립적인 조사 호출의 명시적 묶음을 비교해 반복 context 처리 감소를 보고했다.
   소규모 코딩 조사 실험이며 복지 추출의 성능 보장은 아니다.
7. [긴 CLI context의 비용 증폭 보고 #44884](https://github.com/openai/codex/issues/44884):
   사용자 telemetry에서 큰 context가 반복 처리되는 현상을 보고했다. 미검증 사용자 보고를
   계정 과금 결함으로 단정하지 않고, 작은 독립 묶음과 usage 관찰을 선택하는 참고로 삼았다.

검증은 실제 모델 대신 합성 응답·격리 SQLite로 묶음 성공/공고별 실패·부분 재개·시간 초과·
예산 소진·버전 변경·다중 페이지·모드 전환·201건 전체 연결을 검사한다. 실제 대표 공고를
사용한 low/medium/high 및 묶음 크기 1/2/4 비교는 운영 usage와 검수 결과가 쌓인 뒤 수행한다.
