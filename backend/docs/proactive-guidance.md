# 사용자 상황에 따른 지속 복지 안내

2026-10-07. 담당: 백엔드·웹 공통.

## 현재 동작

회원이 별도로 저장에 동의한 생활·주거·피해 정보를 계정에 저장한다. 서버의 회원 나이·지역과
결합해 찾아볼 지원 분야를 도출하고, 수집된 최신 공개 공고 전체를 페이지 단위로 비교한다.
주거 개선, 청년 일자리·취업, 거주 지역 재난지원 공고 확인과 직접 확인한 재난 피해 복구가
첫 탐색 분야다. 피해 정보를 아직 입력하지 않았으면 거주 지역과 명확히 연결되는 복구·구호
공고를 먼저 찾아 피해 여부와 발생일을 질문한다. 전국·지역 미확인 공고는 이 지역 탐색에서
제외하며, 공고가 있다는 사실로 실제 재난 발생이나 개인 피해를 확정하지 않는다.

‘자가 주택 준공 후 20년’과 ‘19~34세’는 **탐색을 시작하는 규칙**이다. 공고별 노후주택·청년
자격을 대신하지 않는다. 자가 거주자는 주택 소유 조건에 True를 제공하지만, 현재 임차
거주 중이라는 사실로 다른 주택까지 소유하지 않았다고 가정하지 않는다. 구직 의사와
취업 준비 정보로 실업을 추론하지 않으며, 지역 사건만으로 개인 피해를 만들어내지 않는다.

공개 원문의 키워드와 인용 근거로 후보를 연결하고 기존 참/거짓/미확인 조건 비교를 재사용한다.
확인된 불충족·마감·예산 소진 공고는 현재 후보에서 제외한다. 미확인 조건은 질문으로
남기며, 공개 상태와 전체 조건이 준비되지 않은 공고를 신청 가능으로 확정하지 않는다.
취업·주택 상황과 관련된 분야를 계속 살펴보므로 관심 태그를 직접 고르지 않아도 탐색한다.

웹의 내 비서·내 정보에서 상황 입력, 동의 후 저장, 지속 안내 켜기/중지, 현재 후보 확인,
지원 진행 상태 변경, 알림 읽음, 선택정보 삭제를 제공한다. 금융 원입력은 이 기능에서
자동 재사용하지 않는다. 외부 AI로 개인정보를 전송하지 않는다.

## 운영 초기화와 정기 확인

백엔드 디렉터리에서 이미 초기화한 회원 저장소에 세 개의 테이블만 추가한다.
HTTP 요청은 운영 MySQL의 스키마를 자동 변경하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m app.modules.monitoring --init
.\.venv\Scripts\python.exe -m app.modules.monitoring --once
.\.venv\Scripts\python.exe -m app.modules.monitoring --watch --interval 300
```

`--init`: 계정별 생활 프로필·지원 진행·알림 테이블 추가. 기존 회원·공고 데이터 보존.
`--once`: 활성화한 계정 전체를 한 번 확인. `DB_ENABLED=true`와 기존 공개 공고 MySQL 필요.
`--watch`: 기본 300초마다 재평가. `--interval` 최소 30초, `--batch-size` 기본 100/최대 1000.
브라우저·로그인 세션의 수명과 무관하게 실행하며 Ctrl+C로 종료한다.

운영에서는 이 독립 worker를 서버의 서비스/프로세스 관리로 상시 실행해야 한다. 이번 변경은
운영 예약 작업을 설치하거나 자동으로 기존 서버를 재시작하지 않는다. 정보 수집의 실제
주기는 기존 ingestion 설정에 따르며, worker는 **이미 수집·공개된 공고**를 재평가한다.

## 저장·동시성·알림

각 프로필의 UUID 버전을 읽고 조건 비교를 수행한 뒤, 활성 상태와 버전이 그대로일 때만
후보·새 알림·확인 시각을 같은 트랜잭션으로 반영한다. 도중에 중지·삭제·정보 변경·회원
탈퇴가 일어나면 이전 작업이 새 정보를 덮거나 삭제 데이터를 다시 생성하지 않는다.
탈퇴는 새로운 선택정보·진행 이력·알림과 관련 호출 제한 기록도 삭제한다.

같은 공고가 여러 탐색 분야에 연결돼도 신청 상태는 공고 단위로 공유한다. 지역 재난 공고
확인에서 피해 복구 안내로 바뀌어도 기존 준비·신청·완료·해당 없음 상태를 이어받는다.

알림은 공고의 지원 내용·조건·기간·신청 방법과 비교 결과 등 의미 있는 내용의 fingerprint로
중복을 방지한다. 같은 내용을 정기 확인할 때 알림을 반복하지 않는다. 완료·해당 없음으로
표시한 후보의 반복 알림을 억제하고, 신청한 공고는 현재 목록에서 사라져도 진행 상태를 보존한다.
조회 실패는 마지막 성공 시각과 기존 후보를 유지하며, ‘지원 없음’으로 바꾸지 않는다.

현재 알림은 계정의 **앱 안 알림 내역**이다. 실제 이메일·Expo 푸시 전송, 공식 재난 API의
자동 사건 감지, 기관 신청 결과 자동 조회는 연결하지 않았다. 지역 재난지원 공고는 피해
미입력 상태에서도 탐색하고, 본인이 피해를 확인하면 복구 지원 탐색으로 이어진다. 발생일이
없으면 날짜를 추정하지 않고 확인 질문을 남긴다. 피해가 없다고 입력하면 해당 지역 재난
탐색을 중단한다. 최신 알림 100개와 전체
미읽음 수를 반환한다.

## HTTP 계약·검증

[`modules/monitoring/readme.md`](../app/modules/monitoring/readme.md)에서 함수와 CLI 계약,
[`api-management.md`](../../api-management.md)에서 HTTP 계약을 관리한다.
계정 ID는 웹 쿠키 또는 모바일 Bearer 인증으로 결정한다. POST는 `X-Auth-Request: 1`,
엄격한 JSON 입력·명시적 저장 동의를 요구한다. 모든 응답은 `Cache-Control: no-store`다.

검증은 합성 공고를 사용하는 격리 DB에서 탐색 규칙·공고 페이지 처리·미확인/불충족,
중복 알림·신청 상태 보존·중지/삭제와 지연 작업·탈퇴·회원 격리·입력 반영 방지를 확인한다.
실제 외부 공고 수집과 이메일/푸시 발송 테스트를 의미하지 않는다.
