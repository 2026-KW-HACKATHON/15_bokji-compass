# 복지로·행안부 실제 응답과 가공 계획

확인일: 2026-09-21. 상태: 실제 API 조회·기존 파서 재현·가공 방법 검토 완료. 업무 코드·DB 변경 없음.

2026-09-22 후속: 복지로 XML 반복·중첩 손실 수정 및 [rawdata 파싱](raw-parsing.md) 구현. 아래는 최초 조사 시점 기록.

## 1. 실제 조회 결과

| 행안부 Gov24 | serviceDetail | JSON | 5건 | 10,931 |

- 모두 HTTP 200 확인. 복지로 업무 결과 코드 `0`, 메시지 `SUCCESS` 확인.
- 전체 건수는 응답 메타데이터의 조회 시점 값. 전체 수집·전체 데이터 품질 검증 결과와 구분.
- 키 앞뒤 공백·줄바꿈 존재. 기존 공통 요청기의 `strip()` 적용과 같은 처리로 인증 성공. `.env` 원본 보존.
- 원본 응답·구조 분석은 Git 제외 경로 `backend/data/api-inspection/20260921T021315Z/`에 저장. 요청 인증값 저장·출력 없음.
- 인증 확인 과정의 실패 요청도 호출량에 포함될 가능성 고려. 이번 조사에서 실제 전수 수집 미실시.

공식 제공 범위: 행안부는 중앙·지방정부·공공기관 등의 공공서비스 목록과 상세 제공. 복지로는 선정된 중앙부처 복지사업의 목록과 상세 제공. [행안부 공식 안내](https://www.data.go.kr/data/15113968/openapi.do), [복지로 공식 안내](https://www.data.go.kr/data/15090532/openapi.do).

## 2. 행안부 응답 구조

공통 봉투: `currentCount`, `data`, `matchCount`, `page`, `perPage`, `totalCount`.

| 데이터 | 주요 실제 필드 | 가공 방식 |
| --- | --- | --- |
| 식별·출처 | `서비스ID`, `상세조회URL` | ID는 문자열 유지. 선행 0 보존 |
| 기본 정보 | `서비스명`, `서비스목적요약`, `서비스분야`, `소관기관명`, `소관기관코드`, `부서명` | 공통 필드로 직접 매핑 |
| 대상·조건 | `지원대상`, `선정기준` | 문단·항목·예외를 보존한 뒤 조건 단위 분리 |
| 혜택 | `지원내용`, `지원유형` | 혜택 설명과 금액·주기·지원방식 분리 |
| 신청 | `신청기한`, `신청방법`, `접수기관`, `온라인신청사이트URL`, `구비서류` | 신청 기간 상태·반복 회차·제출서류 목록 분리 |
| 출처 시각 | `등록일시`, `수정일시` | 목록의 14자리 시각과 상세의 날짜를 별도 파싱. 원래 정밀도 보존 |
| 지원조건 코드 | `JA0101` 등 `JA*` 48개, `서비스ID`, `서비스명` | 코드·값·자료형 원문 보존 후 공식 코드 사전과 연결 |

- 이번 표본의 목록·상세·조건 ID 집합은 일치. 운영 수집에서는 페이지 순서를 가정하지 않고 `서비스ID`로 결합.
- 목록과 상세의 같은 이름 필드도 의미·정밀도 차이 존재. 단순 `dict.update()` 대신 출처별 원문 보존과 필드별 선택 규칙 적용.
- `신청방법`, `전화문의`, `법령` 등 일부 필드에 `||` 구분자 확인. 해당 필드에 한해 목록화.
- 조건 코드 값은 문자열 `Y`·정수·`null` 혼재. `null`을 `N`, 자격 미충족 또는 제한 없음으로 변환 금지.
- 공개 OAS 조회에서 `paths`·`definitions`가 빈 객체로 반환. 이번 조사에서 JA 코드별 공식 의미는 확정하지 못함. 표본 숫자만으로 나이·소득 코드를 추정 매핑하지 않음.

## 3. 복지로 응답 구조

목록은 `wantedList` 아래 `totalCount`, `pageNo`, `numOfRows`, `resultCode`, `resultMessage`, 반복 `servList`로 구성. 상세는 `wantedDtl` 아래 필드와 반복 항목으로 구성.

| 공통 항목 | 복지로 실제 필드 | 처리 |
| --- | --- | --- |
| 원천 ID·제목 | `servId`, `servNm` | 문자열 매핑 |
| 기관 | `jurMnofNm`, 목록의 `jurOrgNm` | 부처·기관 원문 보존. 부서가 섞인 문자열 임의 분리 금지 |
| 요약 | 목록 `servDgst`, 상세 `wlfareInfoOutlCn` | 목록·상세 요약 구분 |
| 지원대상 | `tgtrDtlCn` | 조건 추출 근거 |
| 선정기준 | `slctCritCn` | 다른 필드 참조 문구도 보존 |
| 지원내용 | `alwServCn` | 실제 필드명 사용. 기존 초안의 `alwnServCn`과 다름 |
| 기준연도 | `crtrYr` | 원문 내 금액 기준연도와 별도 관리 |
| 분류·주기 | `lifeArray`, `trgterIndvdlArray`, `intrsThemaArray`, `sprtCycNm`, `srvPvsnNm` | 분류 문자열과 조건 판정 분리 |
| 신청 단계 | 반복 `applmetList` | 순서 있는 배열로 보존 |
| 연락처 | 반복 `inqplCtadrList` | 배열로 보존 |
| 서식·첨부 | 반복 `basfrmList` | 제목·URL 메타데이터 보존, 첨부 자동 다운로드 미실시 |
| 근거 법령 | 반복 `baslawList` | 배열로 보존 |

- 실제 목록 요청에서 `callTp=O`, `srchKeyCode`, `searchWrd`, `pageNo`, `numOfRows`, `lifeArray`, `charArray`, `desireArray` 사용 후 정상 응답 확인. 검색어·필터는 빈 값으로 조회했으므로 개별 필터 효과는 미검증.
- 상세 요청은 `callTp=D`, `servId` 사용 후 정상 응답 확인.
- 공식 제공 형식은 XML. 코드의 JSON 대역 테스트 통과를 실서비스 JSON 지원 검증으로 취급하지 않음.
- 표본 상세의 `crtrYr`는 2026이나 지원대상 금액 설명에 2025 기준 포함. 전체 숫자를 2026 기준으로 자동 보정하지 않고 검토 이슈로 분리.

## 4. 현재 코드에서 재현한 한계

| 위치 | 확인 결과 | 필요한 변경 |
| --- | --- | --- |
| `collectors/bokjiro_services.py::_xml_item` | 자식의 `.text`만 저장하고 동일 태그를 덮어씀. 실제 상세의 신청 단계 6개·연락처 2개·서식 4개·법령 2개가 빈 문자열로 변환 | 중첩 노드를 재귀 처리, 반복 태그는 항상 배열 유지. 단일 항목도 배열 계약 적용 |
| `normalization/policy.py::_condition_type` | 복합 선정기준을 키워드 우선순위에 따라 한 유형으로 분류. 근로·자녀장려금의 가구·소득·재산·연령 조건이 `age` 하나로 분류 | 문장 단위 다중 조건·대상 주체·AND/OR·예외 구조 분리 |
| `normalization/policy.py::_application_dates` | 표본 5건 모두 시작·종료일 `None`. 상시신청·반복 모집·별도 공고·사건 접수 후를 구분하지 못함 | 날짜 외에 `always_open`, `recurring`, `announcement`, `event_based`, `unknown` 등 기간 종류와 원문 저장 |
| Gov24 수집기 | 현재 공개 함수는 목록 첫 페이지만 조회 | 페이지 순회·상세/조건 조회·ID 결합·수집 체크포인트 추가 |
| 현재 SQL | 원문 조건 중심이며 원천 ID·개정·조건 비교값·논리 구조 없음 | 기존 [구현 계획](implementation-plan.md)의 원천·개정·조건 인덱스 설계와 정합성 확보 |

복지로 표본의 목록 5건·상세 스칼라 필드는 기존 파서에서 정상 확인. 반복 구조 손실은 실제 원본을 기존 파서에 다시 입력하여 재현. 업무 코드 수정은 이번 조사에 포함하지 않음.

## 5. 권장 가공 순서

1. **원본 보존**: 응답 바이트, 공급자, 엔드포인트, 비밀값 없는 요청 인수, 수집 시각, 원본 해시 저장. API 키·Authorization·인증값 포함 URL 제외.
2. **공급자별 파싱**: Gov24 JSON과 복지로 XML을 각각 처리. 중첩·반복·빈 값·원문 위치 보존. 복지로 반복 항목 손실 수정 우선.
3. **공통 정책 매핑**: `provider + source_service_id`를 원천 고유키로 사용. 제목·기관·설명·신청정보·첨부·법령 매핑. 서로 다른 공급자의 동일 사업은 후보 연결만 생성하고 원천별 기록 유지.
4. **조건 후보 추출**: 구조화 코드는 공식 사전 확인 후 결정적 변환. 문장 조건은 규칙 또는 LLM으로 후보 추출하되 원문 필드·문단·근거 필수 연결.
5. **검증·검토**: 값 타입·단위·대상 주체·기준일·AND/OR·예외·원문 일치 검증. 불명확한 조건은 `UNKNOWN`/검토 필요로 유지. 추출 결과만으로 자격 확정 금지.
6. **MySQL 저장**: 원문 참조·정제 JSON·개정·검색용 조건 인덱스를 한 트랜잭션으로 저장. 성공 응답은 커밋 이후. 최초 상태 `draft`, 검토·공개 단계 분리.
7. **변경 수집**: 공급자 ID와 원본 해시 기준 중복 제어. 날짜가 누락되거나 정밀도가 낮은 경우도 해시로 변경 확인. 늦게 완료된 과거 수집이 최신 개정을 덮어쓰지 않도록 관리.

표시용 정리에서는 CRLF/CR을 LF로 변환하고 HTML을 정리하되, 원문은 별도 유지. 번호·들여쓰기·항목 경계를 지워 조건의 논리 관계를 잃지 않도록 처리.

## 6. 조건 구조 예시

아래는 실제 복지로 표본에서 추출할 수 있는 **일부 조건 후보**. 서비스 전체 자격 판정 결과와 구분.

```json
{
  "provider": "bokjiro",
  "source_service_id": "WLF00000026",
  "review_status": "needs_review",
  "candidate_rule": {
    "all": [
      {"field": "applicant.age", "operator": "gte", "value": 19,
       "unit": "year", "reference_date": null, "evidence_field": "tgtrDtlCn"},
      {"field": "applicant.registered_disability", "operator": "eq", "value": true,
       "evidence_field": "tgtrDtlCn"},
      {"field": "household.recognized_income_median_ratio", "operator": "gt", "value": 50,
       "unit": "percent", "evidence_field": "tgtrDtlCn"},
      {"field": "household.recognized_income_median_ratio", "operator": "lte", "value": 100,
       "unit": "percent", "evidence_field": "tgtrDtlCn"}
    ]
  },
  "unresolved": ["나이 기준일", "신용·보증·금융기관 심사 조건", "금액 설명의 기준연도 차이"]
}
```

- 실제 저장 계약에는 원문 해시·문단/문자 범위·추출 버전도 필수 포함.
- 소득인정액과 단순 연소득은 다른 필드. 가구 소득과 신청자 소득도 분리.
- 50% **초과**와 100% **이하**의 경계 연산자 구분.
- 전체 조건과 예외가 완성되지 않은 표본을 PASS로 처리하지 않음.
- Gov24 유아 지원의 나이는 신청 보호자 나이와 구분. 부양자녀·부모·가구 조건을 신청자 조건으로 일괄 변환 금지.

## 7. 구현 우선순위와 검증 기준

1. 복지로 중첩 XML 손실 수정 + 반복 항목 0/1/여러 개 합성 fixture 테스트.
2. Gov24 페이지·상세·조건 ID 결합 + 코드 사전 확인. 누락·중복 ID와 부분 실패 테스트.
3. 공급자별 공통 매핑 + 신청기간 종류·원천 시각 정밀도·기준연도 경고 테스트.
4. 조건 후보·근거·주체·논리 계약 + 기존 키워드 분류 대체. 금액·퍼센트 경계, 예외, UNKNOWN 테스트.
5. MySQL 영속 저장·개정·수집 재시작 테스트.

복지로 공식 안내의 개발계정 신청 가능 트래픽은 100, 행안부는 10,000으로 표기. 실제 계정 한도·기간은 활용신청 화면에서 확인 후 배치 크기·상세 호출량 결정. 전체 상세 수집을 한 번에 실행하지 않고 체크포인트·캐시·한도 오류 처리를 먼저 구성. [복지로 이용 안내](https://www.data.go.kr/data/15090532/openapi.do), [행안부 이용 안내](https://www.data.go.kr/data/15113968/openapi.do).

이번 결과는 제공 데이터의 구조·가공 가능성 검토. 복지 지원 자격이나 금융상품 이용 가능 여부에 대한 개인별 판단은 포함하지 않음.
